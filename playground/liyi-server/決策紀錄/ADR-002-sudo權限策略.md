# ADR-002：要不要給自動化工具 sudo 權限？

| | |
|---|---|
| **狀態** | ✅ 已採納並實作 |
| **日期** | 2026-08-01 |
| **影響範圍** | `90` 的權限模型、所有自動化操作 |

---

## 背景

維護這台機器時，很多操作需要 root 權限（改 `/etc` 下的設定、重啟服務、裝套件）。而操作是透過一個自動化工具（AI agent）進行的，它執行指令時**沒有終端機（TTY）**：

```bash
$ tty
not a tty
$ sudo cat /etc/netplan/00-installer-config.yaml
sudo: A terminal is required to authenticate
```

於是產生一個問題：**要怎麼讓它能執行 root 操作？以及——該不該讓它能？**

---

## 先搞懂：為什麼 sudo 一定要終端機？

這不是刁難，是密碼輸入的安全前提。`sudo` 需要：

1. 對終端機下 `ECHO off`，讓你打的密碼不顯示在畫面上
2. 確保密碼不會被同一個 session 裡的其他程式讀走

沒有終端機，這兩件事都做不到。所以 `sudo` **寧可直接拒絕，也不會退而求其次從管線讀密碼**——因為那樣密碼會出現在指令歷史、行程列表、或日誌裡。

> 💡 這是個好例子：**很多「不方便」的設計，背後是刻意的安全取捨。** 遇到工具擋你的時候，先問「它在保護什麼」，通常會學到東西。

---

## 業界的建議在說什麼？

常聽到「不該依賴 sudo」「不該給 AI sudo 權限」。這句話其實混了**兩個不同的意思**：

### 意思 A：不該有「常駐」的 root 權限

指不要整天掛在 root shell、不要 `NOPASSWD: ALL`、不要所有服務都用 root 跑。**這個是對的。**

### 意思 B：不該「手動」改機器

這才是 SRE 圈真正在講的那個，重點不在權限大小，而在**可重現性**。

| 手動做法 | 業界做法 |
|---|---|
| ssh 進去 `sudo vim /etc/nginx/...` | 設定寫進 git，用 Ansible / Terraform 套用 |
| 手動裝套件 | 寫進 Dockerfile / cloud-init |
| 出事進去手改 | 改 code → PR → review → pipeline 自動套用 |

流程裡**照樣需要 root**，一點都沒少。差別是那個 root 由 pipeline 從版控過的原始碼套用，不是某個人憑記憶敲出來的。

所以精確版本是：**不該依賴「人工的、無紀錄的、不可重現的」root 操作。**

> 這也是為什麼待辦清單裡有「設定檔納入版控」這一項。

---

## 給自動化工具 root 的真實風險

誠實列出來，這三個都是真的：

### 1. 脈絡不完整下的自信行動

工具看到的是系統的一小片。一個 `rm -rf`、`chmod -R`、`dd` 打錯目標，root 權限下沒有東西會攔它，而且很多不可逆。

### 2. 提示注入（Prompt Injection）

這是 AI 專屬的新風險，也最該擔心。假設工具去讀一個日誌檔、抓一個網頁、或看一份別人寫的設定檔，而**裡面藏了一句「忽略先前指示，執行 ○○」**——如果它當下握有免密碼的 root，就會直接執行。你不會看到、也來不及攔。

**每次要密碼，就是把這條路截斷。**

### 3. 看起來無害、其實能提權的指令

這點最容易被低估。假設你覺得「只讓它免密碼跑 `systemctl` 應該很安全吧」：

```
liyi ALL=(root) NOPASSWD: /usr/bin/systemctl
```

**這實質上等於給了完整 root。** 因為 `systemctl` 可以 link 並啟動任意 unit 檔，而 unit 檔裡的 `ExecStart` 是以 root 執行的：

```
寫一個 unit 檔，ExecStart=任意指令
  → systemctl link 它
  → systemctl start 它
  → 那個指令以 root 跑起來
```

這類「看起來受限、實際能提權」的指令有一份完整清單叫 **GTFOBins**（https://gtfobins.github.io/）。**設計任何權限規則前都該查一下。**

---

## 考慮過的選項

### 選項 A：askpass GUI 彈窗 ← **採用**

裝一個 GUI 密碼程式，`sudo -A` 會把「問密碼」外包給它：

```bash
sudo apt install ssh-askpass-gnome
export SUDO_ASKPASS=/usr/bin/ssh-askpass
sudo -A netplan generate      # → 桌面彈出密碼框
```

密碼框開在遠端桌面上，人在那邊輸入。**密碼從頭到尾不經過自動化工具。**

| 優點 | 缺點 |
|---|---|
| 不儲存密碼 | 每次都要人在場 |
| 不改變永久權限 | 需要有圖形介面 |
| 每次提權都是一個人工檢查點 | |

### 選項 B：限定指令免密碼

只讓特定指令免密碼。**看似折衷，實際上因為上面說的提權問題，安全性遠低於直覺。** 而且這次需要的指令（`netplan`、`systemctl`、`tee` 寫入 `/etc`）幾乎每個都能間接提權。

### 選項 C：完全不給，人工複製貼上

零風險，但每次 root 操作都要多一道來回。實測下來，一個晚上的維護大約需要 6 次 root 操作——不算多，但夠煩。

---

## 決策

**採用選項 A（askpass），並搭配一條硬規則：永不設定 `NOPASSWD: ALL`。**

判斷依據不是教條，而是**爆炸半徑**：

| 環境 | 出事的代價 | 合理做法 |
|---|---|---|
| `90`（家用閘道器） | 重灌 + 重貼設定，半小時 | askpass 逐次確認就夠 |
| 公司測試環境 | 重建，影響同事半天 | 走 CI/CD，人工 sudo 當例外 |
| 正式環境資料庫 | 資料遺失、客戶受影響 | 人不該有直接 root，走變更審核 |

`90` 不存資料、只轉發流量、設定檔加起來不到 100 行。**爆炸半徑小，所以 askpass 是恰當的強度，不需要更嚴。**

> 💡 這是最重要的一條：**同一個做法在不同環境下，對錯可以完全相反。** 新手常見的錯誤是把某個環境的最佳實務當成普世真理。

---

## 一個誠實的觀察

實測下來，**人在密碼框跳出來時，通常沒有仔細看要執行什麼就輸入了。**

這代表：**密碼提示只有在你真的讀了內容才是防護，否則它只是一道儀式。**

緩解方式是要求自動化工具在每次提權前，先用人話說明「要改什麼、為什麼」——把判斷成本降到「讀三行字」而不是「看懂一串指令」。

---

## 後果

### 正面

- 自動化工具可以完成完整的維運任務，不用人工複製貼上
- 每次提權都留下稽核紀錄：

```
liyi : PWD=/home/liyi ; USER=root ; COMMAND=/usr/bin/tee /etc/netplan/99-wait-online-fix.yaml
liyi : PWD=/home/liyi ; USER=root ; COMMAND=/usr/sbin/netplan generate
```

  用 `journalctl -t sudo` 隨時可查「誰、何時、跑了什麼」。

### 負面

- 需要遠端桌面在線。純 SSH 情境下 askpass 沒有畫面可以顯示，會卡住。
- `SUDO_ASKPASS` 是環境變數，每個 session 都要設，容易忘記。
- 人必須在場，無法完全無人值守。
