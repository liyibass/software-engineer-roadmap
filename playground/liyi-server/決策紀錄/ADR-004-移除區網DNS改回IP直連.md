## 背景

[ADR-001](ADR-001-路徑式vs子網域路由.md)（2026-08-01）決定改用子網域路由：在 `90` 架
dnsmasq 當區網 DNS，服務網址變成 `http://grafana.liyibass.internal/`。

**10 天後回退。** 這份 ADR 記錄為什麼。

---

## 觸發事件

一台區網內的 Windows 開 `http://grafana.liyibass.internal/` 連不上。排查結果：

```
Windows 拿到的 DNS（DHCP 下發）  →  192.168.10.1、8.8.8.8
```

兩個都不認識 `liyibass.internal`（`.internal` 是 ICANN 保留給私有網路的，公共 DNS
一定回 NXDOMAIN）。而 Mac 之所以一直正常，是因為它的 DNS **被手動設過** `192.168.10.90`。

也就是說：**這套名稱解析從來沒有真正「對整個區網」生效過**，只對設定過的那一台生效。
ADR-001 的實作計畫第 5 步「讓區網裝置使用 90 當 DNS（路由器 DHCP 下發）」是整個方案
的地基，而它是唯一一步**不在自己機器上、無法版控、無法用腳本重現**的設定。

> 💡 **這是這次最值得記住的一課**：一個方案如果有任何一步落在你管不到、也記錄不了的
> 地方（別人的路由器、雲端主控台、某個同事的手動操作），那一步就是它真正的可靠度上限。
> 其他步驟做得再嚴謹都補不回來。

---

## 檢驗 ADR-001 的前提

ADR-001 採用子網域的**核心論證**是：

> 未來規劃：98 上會裝**很多**自己的服務，還會多一台 97 當第二個 worker。
> 也就是說，**分流規則會從 1 條變成 10 條以上**。
>
> 關鍵理由是**時機**：現在只有一個服務，遷移成本最低。

這個推理本身沒有錯——「改變成本隨時間上升的決定要提早做」是對的。但它建立在一個**預測**上：
服務數量會快速成長。

**10 天後，服務數量仍然是 1。** 97 沒有部署，98 上沒有加新服務。

為了「未來會有 10 個服務」而預先承擔的複雜度——一個額外的 daemon、一個新的單點故障、
一份無法版控的路由器設定、每台新裝置的手動設定成本——**全部都在為一個還沒發生、也不知道
何時發生的情境付費**。

> 💡 提早決定的前提是**你對趨勢的判斷可靠**。當「未來會怎樣」本身就是猜測時，
> 提早決定只是把猜測的成本提前支付。這種時候，**保持簡單、等訊號出現再改**通常更划算——
> 尤其當回退成本也很低的時候（這次回退的**主體**只花了幾十分鐘——收尾則拖了一天，見[後記](#後記於實作一天後才發現沒做完)）。

---

## 考慮過的選項

### 選項 A：修好 DNS 下發，繼續用子網域

把路由器 DHCP 的 DNS（option 6）改成 `192.168.10.90`，讓所有裝置自動拿到。

| 優點 | 缺點 |
|---|---|
| 保留有語意的網址 | **全區網的 DNS 都要經過 90** — 它掛掉，全家連不上網（不只是內部服務） |
| 不用改 nginx | 90 跑在 **WiFi 筆電**上（見 [ADR-003](ADR-003-網路介面與IP規劃.md)），拿它當全家 DNS 太重 |
| | 路由器設定無法版控，換路由器就要重做 |
| | Windows 還有 DoH / 瀏覽器安全 DNS 會繞過區網 DNS 的坑要處理 |

### 選項 B：回到路徑式 `http://192.168.10.90/grafana/`

| 優點 | 缺點 |
|---|---|
| 保留 `90` 的導覽首頁，根路徑還空著 | 需要 Grafana 開 `serve_from_sub_path` + 設 `root_url` |
| 未來加服務有分流空間 | **正是 ADR-001 逃離的那組問題**（前綴剝除、前端資源路徑、`proxy_pass` 尾斜線） |
| | 每加一個服務都要賭它支不支援 sub-path |

### 選項 C：IP 直連，Grafana 佔住根路徑 ← **採用**

nginx 只留一個 `server` 區塊，設成 `default_server`：

```nginx
server {
    listen 80 default_server;
    server_name _;

    location / {
        proxy_pass http://192.168.10.98:3000;
        include    snippets/proxy-headers.conf;
    }
}
```

| 優點 | 缺點 |
|---|---|
| **零外部依賴**：不需要 DNS、不需要路由器配合、不需要每台裝置設定 | 網址沒有語意（`192.168.10.90` vs `grafana.…`） |
| Grafana 仍住在根路徑，**sub-path 的坑一個都不用踩** | **根路徑被佔用**，加第三個服務時沒有分流空間 |
| `98` 完全不用動設定（除了 `root_url`） | |
| `default_server` 接住所有 Host，舊書籤 / DNS 快取也能落地 | |
| 少一個 daemon、少一個單點故障、nginx 少一層啟動依賴 | |

---

## 決策

**採用選項 C。**

理由是**把複雜度推遲到真正需要的時候**。目前只有一個服務要對外，最簡單的方案就足夠；
選項 A 和 B 都是在為「未來會有很多服務」付費，而 ADR-001 已經示範過那個未來不一定會來。

至於「根路徑被佔用、加第三個服務時沒空間」——那是**未來的問題，而且屆時訊號很明確**
（真的有第二個服務要上線了）。到時再依當下的實際需求選：不同的 port、重新引入 DNS、
或直接上 k3s + Ingress。**那時的資訊會比現在多。**

> 💡 這跟 ADR-001 的判斷框架其實是同一套，只是套用結果相反。
> 差別在於**回退成本**：子網域 → IP 的回退只花了幾十分鐘（改一個 nginx 檔、一個環境變數、
> 停一個服務）。回退成本低的決定，就不需要提早鎖定。
>
> ⚠️ 事後補充：這句話當時寫得太早。「停一個服務」那步**當天並沒有做**，
> dnsmasq 又活了一天。低回退成本指的是**動手的成本**，不等於**已經動完手**。

## 實作

| # | 位置 | 動作 | 實際完成 |
|---|---|---|---|
| 1 | 路由器 | DHCP 的 DNS 改回 `192.168.10.1`（不再下發 90） | 08-11 |
| 2 | `90` | nginx `gateway` 改為單一 `default_server`，移除子網域 `server_name` 與靜態導覽頁 | 08-11 |
| 3 | `90` | `/grafana/` 的 301 從「導向 `.internal` 名稱」改為「導回 `/`」，救回舊書籤 | 08-11 |
| 4 | `98` | `GF_SERVER_ROOT_URL` → `http://192.168.10.90/`，重建容器 | 08-11 |
| 5 | `~/infra` | 移除 dnsmasq 鏡像與 `sync.sh` 的拉取行 | 08-11 |
| 6 | `90` | 移除 `/etc/systemd/resolved.conf.d/liyibass.conf`，`systemctl restart systemd-resolved` | **08-12** |
| 7 | `90` | `systemctl disable --now dnsmasq`，移除 `/etc/dnsmasq.d/local.conf` | **08-12** |
| 8 | `90` | `apt purge dnsmasq dnsmasq-base` + `autoremove --purge`（連帶移除 `dns-root-data`） | **08-12** |
| 9 | `90` | ufw 移除 53 埠規則（`ufw delete` 掉 `53 ALLOW IN 192.168.10.0/24`） | **08-12** |

> 第 6 步**在原本的實作計畫裡不存在**——它是移除當天才發現的。詳見下方後記。

### 順序很重要

**第 1 步必須在第 7 步之前。** 如果路由器還在下發 `90` 當 DNS 就把 dnsmasq 停掉，
全區網會立刻失去 DNS——不只是內部服務連不上，是整個上網都解析不了。

**第 6 步也必須在第 7 步之前**，理由同構，只是對象變成 `90` 自己：
`/etc/systemd/resolved.conf.d/liyibass.conf` 把這台的 global DNS 指向 `192.168.10.90`，
先停 dnsmasq 的話，這台自己的 resolver 就指著一個死掉的 server。
兩者是同一個規律——**先解除所有「指向它」的設定，最後才停掉它本身**。

同理，**第 4 步不能漏**。`GF_SERVER_ROOT_URL` 只影響 Grafana 產生的**絕對**連結
（告警通知、Share URL、快照），一般瀏覽走的是相對路徑。所以設錯時**平常完全看不出來**，
等到收到告警、點下去發現連結是死的才知道。這種「沉默的錯誤」比當場壞掉的還難查。

### `sync.sh` 的連帶傷害

`~/infra/sync.sh` 開頭是 `set -euo pipefail`，裡面有一行：

```bash
pull_root /etc/dnsmasq.d/local.conf   /etc/dnsmasq.d/local.conf
```

檔案一旦刪除，`cat` 失敗 → 整個腳本中止 → 後面的 netplan、systemd、98 的 rsync 全都拉不到。
**移除服務時，記得檢查有沒有工具腳本正在引用它的檔案。**

## 後記：於實作一天後才發現沒做完

這份 ADR 原本在 2026-08-11 就標成「✅ 已實作」。**但當天只做完第 1–5 步，第 6–9 步都沒做。**

隔天（08-12）順手問了一句「這台的內部 DNS 已經移除了嗎？」，查出來的是：

```
Active: active (running) since Wed 2026-08-12 06:04:30 CST
/etc/dnsmasq.d/local.conf                       還在
dnsmasq.service                                 enabled（開機自動啟動）
192.168.10.90:53                                還在聽
```

dnsmasq 不只沒停，還跟著開機起來了。**問這句話的是寫下這份 ADR 的人本人**——
連作者都不確定文件寫的是不是真的，這件事本身比那三步沒做更值得記下來。

### 為什麼查不出來

因為**表面上完全正常**。08-11 做完第 1–4 步之後：

- 使用者體驗：`http://192.168.10.90/` 開得起來 ✅
- 舊網址：路由器已不下發 90，`grafana.liyibass.internal` 本來就解析不到 ✅（符合預期）
- dnsmasq 還活著：**沒有任何症狀**——沒人問它，它就只是閒著

移除類的工作有個特性：**沒做完的部分不會報錯**。新增功能沒做完，功能就是壞的，你馬上會知道；
移除沒做完，殘留物只是安靜地待著，繼續佔記憶體、繼續開機啟動、繼續聽 53 埠。
**沒有回饋迴路**，只能靠主動去查。

### 漏掉的那一步：`/etc/systemd/resolved.conf.d/liyibass.conf`

```ini
[Resolve]
DNS=192.168.10.90
Domains=~liyibass.internal
```

這個檔案**在原本的 7 步實作計畫裡完全不存在**，[實戰筆記 02](../實戰筆記/02-三套DNS與自架區網解析.md)
當初也沒記錄它是怎麼建的。它的作用是讓 `90` **自己**也能解析 `*.liyibass.internal`——
因為 dnsmasq 設了 `except-interface=lo`，只綁 `192.168.10.90`，
而本機程式走的是 `127.0.0.53`（systemd-resolved），碰不到 dnsmasq。

如果照原計畫只做「disable dnsmasq」，這台的 global DNS 就會指向一個死掉的 server。

> 💡 **教訓**：架設時「為了讓它動起來」臨時加的設定，最容易在拆除清單裡缺席——
> 因為它不在你腦中那條主線上（主線是「裝 dnsmasq、寫設定、開服務」），
> 它是主線的補丁。**拆除清單不能靠回憶，要靠 grep**：
>
> ```bash
> grep -rl '192.168.10.90\|liyibass.internal' /etc/
> ```
>
> 這行如果 08-11 跑過，就會直接指出 `resolved.conf.d/liyibass.conf`。

### 版控鏡像和真機，各自漂移了一邊

第 9 步（ufw 移除 53 埠）也沒做。但這一步的漂移方向**跟前面相反**，值得單獨記：

| | 53 埠規則 |
|---|---|
| `~/infra/90-jump/ufw-rules.sh`（版控鏡像） | ✅ 08-11 就刪掉了 |
| `架構現況.md` 的 ufw 表格 | ✅ 08-11 就沒有它了 |
| **`90` 上的實際 ufw** | ❌ **一直留到 08-12** |

也就是說：**文件是對的、版控鏡像是對的，只有機器是錯的。**

這比「文件忘記更新」更難發現。文件過期時，你去看機器就會發現不一致；
但當文件和鏡像**互相印證**、只有真機落單時，你會有兩份「證據」告訴你事情做完了。
`~/infra` 這種設定鏡像的價值在於可重現，**但它記錄的是「應該長怎樣」，不是「現在長怎樣」**——
它是意圖，不是事實。

> 💡 判斷「做完了沒」的唯一權威是**機器本身**：`systemctl is-active`、`ss -tulnp`、`ufw status`。
> 文件和 git repo 都只是二手轉述。二手來源彼此一致，不會讓它們變成一手。

### 對「活文件」的修正

[架構現況.md](../架構現況.md) 開頭寫著「**這是一份活文件**：每次動這些機器之後就更新它」。
這次暴露的失效模式不是「忘記更新」，而是**更新得比現實早**——
文件描述的是**打算做的事**，不是**已經發生的事**。

> 💡 之後 ADR 的「狀態」欄改成兩段式：決策日期與**實際完成**日期分開記。
> 兩者不同時，中間那段落差就是這種漂移的溫床。
> 更好的做法是**先執行、再標完成**，而不是寫計畫時就順手把狀態填成「已實作」。

## 後果

### 正面

- 新裝置**零設定**即可存取：打開瀏覽器輸入 `192.168.10.90` 就好
- 少一個 daemon、少一個單點故障
- nginx 不再等 `nss-lookup.target`（ADR-001 記錄的那層啟動依賴消失了）
- 沒有任何一步落在路由器上——整套設定都在自己的機器裡、都能版控

### 負面（誠實記錄）

- **網址沒有語意**。`192.168.10.90` 記不住，也看不出是什麼服務。書籤或家用入口頁可以緩解。
- **根路徑被 Grafana 佔用**。加第三個服務時，既沒有名稱可分流、也沒有空的根路徑可用。
- **IP 變更的爆炸半徑變大**。原本可以「只改 DNS 一個地方」的幻想沒了——不過 ADR-001 之後
  也發現那是幻想：nginx 的 upstream 預設**只在啟動時解析一次**，IP 變了不會自動跟上。
  現在誠實地用 [架構現況.md](../架構現況.md) 的「IP 遷移 checklist」管理。
- **TLS 之路變窄**。IP 位址的憑證只能自簽（公開 CA 不簽私有 IP）。真的要上 TLS 時，
  很可能得把 DNS 加回來——但那時的需求會明確得多。

---

## 什麼情況下會再回到子網域？

寫下來，免得下次又憑感覺決定：

- 對外服務達到 **3 個以上**（不是「規劃中」，是真的跑起來了）
- 要上 **TLS**，且不接受自簽憑證的瀏覽器警告
- 有 **90 以外的機器**可以當 DNS（不是跑在 WiFi 筆電上的那台）

前兩條任一成立就值得重新評估；第三條是重新評估時的前置條件。

到那時，比 dnsmasq 更值得考慮的選項是 **k3s + Ingress**——它把名稱路由和服務部署
一起解決，而不是額外多養一個 daemon。
