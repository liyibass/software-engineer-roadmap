# ADR-003：網路介面與 IP 規劃

| **日期** | 2026-08-01 |
| **影響範圍** | `90` 的網路設定、未來 `97` 的部署 |

## 背景：一顆還沒引爆的地雷

`90` 有兩張網卡：

| 介面 | 型態 | 目前狀態 | 設定的 IP | 路由 metric |
|---|---|---|---|---|
| `wlp2s0b1` | WiFi | ✅ 使用中 | `192.168.10.90` | 600 |
| `enp1s0f0` | 有線 | ❌ 沒插線（`no-carrier`） | **`192.168.10.97`** | **100** |

問題有兩個，而且會同時爆炸。

### 問題 1：IP 撞號

`192.168.10.97` 正是規劃給**未來第三台機器**的 IP。現在因為沒插線所以還沒衝突，但只要哪天：

- 有人把網路線插上 `90`，**而且**
- `97` 那台機器也部署了

兩台機器就會宣稱自己是 `192.168.10.97`。區網上會出現 ARP 衝突，症狀是**間歇性、隨機、極難查**——有時連得到，有時連不到，取決於哪一台的 ARP 回應先到。

> 💡 IP 衝突是網路故障裡最惡名昭彰的一種，因為它不會乾脆地壞掉，而是**時好時壞**。查這種問題會浪費非常多時間。

### 問題 2：路由優先權會被搶走

Linux 用 **metric** 決定多條路由的優先順序，**數字小的優先**：

```
enp1s0f0  metric 100   ← 較小，優先
wlp2s0b1  metric 600
```

所以只要有線網卡一插上，它會**立刻搶走預設路由**。而且此時這台機器的位址變成 `.97`，於是：

- Nginx 的 `server_name 192.168.10.90` 對不上
- ufw 規則裡針對 `.90` 的假設失效
- 98 的 Prometheus 抓 `192.168.10.90:9100` 抓不到
- 遠端桌面連線中斷

**一個「插網路線」這種看起來人畜無害的動作，會讓整套服務失聯。**

---

## 這個設定是怎麼來的？

```yaml
# /etc/netplan/00-installer-config.yaml
# This is the network config written by 'subiquity'
```

`subiquity` 是 Ubuntu Server 的安裝程式。這是**安裝當下填的值**，後來規劃改變（改用 WiFi、`.97` 留給新機器）但這個檔案沒有跟著更新。

> 💡 這就是**設定漂移（configuration drift）**的典型案例：系統的實際設定，跟你腦中以為的設定，隨時間慢慢分岔。而且通常是在出事的時候才發現。
>
> 這也是「設定檔要納入版控」的理由之一——如果這個檔案在 git 裡，`.97` 這個值會在某次 review 時被看見。

---

## 順帶發現：閘道器走 WiFi 合理嗎？

`90` 是所有流量的統一入口，但它走 WiFi。這代表**整個架構的可靠度上限，就是這條 WiFi 的可靠度**。

一次隨手的測試：

```bash
ping -c2 192.168.10.98
# 2 packets transmitted, 1 received, 50% packet loss
```

> ⚠️ **這個數據不能下結論**——只發 2 個封包，樣本太小，可能只是剛好碰到一次重傳。要判斷 WiFi 品質應該跑 `ping -c 100` 看長期丟包率。**記錄在這裡是為了提醒自己去驗證，不是當作證據。**
>
> 這是很重要的自我紀律：**區分「我觀察到的」和「我證明了的」。** 把弱證據當強證據，是除錯時最常見的翻車原因（見 [實戰筆記 01](../實戰筆記/01-開機慢兩分鐘的追查.md) 裡猜錯 WiFi 的那一段）。

而諷刺的是：**這台機器有一個閒置的有線網孔**，只是被設定成錯的 IP。

---

## 考慮過的選項

### 選項 A：把 `enp1s0f0` 的 IP 改掉，繼續走 WiFi

最小改動。把 `.97` 改成別的（或改成不設定 IP），消除撞號與路由搶奪。

| 優點 | 缺點 |
|---|---|
| 五分鐘就好，不用碰實體 | 沒解決 WiFi 可靠度問題 |
| 零風險 | |

### 選項 B：`90` 改走有線，WiFi 當備援

把網路線插上，`enp1s0f0` 設成 `192.168.10.90`，WiFi 改成備援或關掉。

| 優點 | 缺點 |
|---|---|
| 大幅提升可靠度（有線 >> WiFi） | 需要實體操作（牽線） |
| 同時解決撞號問題 | **切換過程會斷線**，而目前的遠端連線正是走 WiFi |
| 延遲更低更穩定 | 需要規劃「切換時把自己鎖在門外」的退路 |

### 選項 C：兩張網卡都用，做容錯（bonding）

用 Linux bonding 把兩張網卡綁成一個邏輯介面，一條斷了自動切換。

| 優點 | 缺點 |
|---|---|
| 真正的高可用 | 設定複雜，WiFi + 有線混合 bonding 支援度不佳 |
| | **對這個規模來說過度設計** |

---

## 傾向（尚未定案）

**先做選項 A 止血，再擇期做選項 B。**

理由是兩者的**急迫性不同**：

- 撞號是「地雷」——平常沒事，踩到就炸，而且可能在最不方便的時候（例如你剛好在部署 `97`）
- WiFi 可靠度是「慢性病」——一直存在，但不會突然致命

先用五分鐘拆掉地雷，慢性病可以排時間好好治。

> 💡 這是實務上很常用的優先順序判斷：**先處理「會突然爆炸」的，再處理「一直很爛」的。** 前者的期望損失更高，因為它會在你沒準備的時候發生。

## 後果（若採用 A + B）

### 正面

- 消除 IP 撞號地雷，`97` 可以安全部署
- 消除「插網路線就整組壞掉」的意外
- （B）整體架構可靠度提升

### 負面

- （B）切換過程有斷線風險，需要現場或有退路
- （B）之後 `90` 依賴實體線材，搬動機器的彈性降低
