## 背景

`90` 是統一入口，所有外部請求先到它，再依規則轉發到內網機器。目前只有一個服務（98 的 Grafana），用**路徑**來分流：

```nginx
location /grafana/ {
    proxy_pass http://192.168.10.98:3000;
}
```

網址長這樣：`http://192.168.10.90/grafana/`

未來規劃：98 上會裝**很多**自己的服務，還會多一台 97 當第二個 worker。也就是說，**分流規則會從 1 條變成 10 條以上**。

---

## 問題

路徑式路由有個隱性成本，而且在只有一個服務時感受不到。

現有設定檔裡已經留下了掙扎的痕跡：

```nginx
# ⚠️ 這裡的 proxy_pass 結尾「不能」加斜線。
# 因為 Grafana 那邊設了 serve_from_sub_path=true，它預期收到的路徑「包含」
# /grafana 前綴，自己會處理。若這裡寫成 proxy_pass http://grafana_backend/;
# （帶尾斜線）Nginx 會把 /grafana 剝掉，Grafana 反而找不到路由 → 一直 404 或跳轉迴圈。
```

這段註解說明了一個真實踩過的坑。**問題是這個坑每加一個服務就要重踩一次**，而且不是每個應用都像 Grafana 一樣提供 `serve_from_sub_path` 這種設定。

### 為什麼掛在子路徑下這麼容易壞？

用一個類比：想像你把某人的家整個搬進另一棟大樓的 3 樓。他家裡所有寫著「往左走到廚房」的紙條都還在，但現在「左邊」已經不是廚房了。

網頁應用也一樣。很多應用在產生 HTML 時會寫死絕對路徑：

```html
<script src="/static/app.js"></script>
<img src="/logo.png">
```

當它被掛在 `/grafana/` 底下，瀏覽器會去要 `http://90/static/app.js`——**少了 `/grafana` 前綴**，Nginx 不知道這是誰的，回 404。畫面就變成一片空白或跑版。

應用要能正確運作，它必須「知道自己被掛在哪個前綴下」並改寫所有路徑。**有些應用支援（Grafana 的 `serve_from_sub_path`），有些部分支援，有些完全不支援。**

---

## 考慮過的選項

### 選項 A：維持路徑式路由

```
http://192.168.10.90/grafana/   → 98:3000
http://192.168.10.90/app/       → 98:8080
```

| 優點 | 缺點 |
|---|---|
| 不需要額外基礎設施 | 每加一個服務都要賭它支不支援 sub-path |
| 不用記域名 | `proxy_pass` 尾斜線規則容易搞錯 |
| 現在就是這樣，零遷移成本 | 前端資源路徑可能壞掉，且**症狀難查**（畫面空白，日誌不一定有錯） |

### 選項 B：子網域路由 ← **採用**

```
http://grafana.liyibass.internal   → 98:3000
http://app.liyibass.internal       → 98:8080
http://worker.liyibass.internal    → 97:xxxx
```

Nginx 設定變得極簡：

```nginx
server {
    server_name grafana.liyibass.internal;
    location / {
        proxy_pass http://192.168.10.98:3000;
    }
}
```

| 優點 | 缺點 |
|---|---|
| 應用認為自己就住在根路徑 `/`，**幾乎都能直接跑** | 需要區網 DNS |
| 設定單純，不用處理前綴剝除 | 要記域名（但比記埠號容易） |
| 網址有語意，一看就知道是什麼服務 | 初期要多做一次設定 |
| 未來要加 TLS 時，憑證好處理 | |

### 選項 C：每個服務開一個埠

```
http://192.168.10.90:3000  → Grafana
http://192.168.10.90:8080  → App
```

現有設定的註解已經明確否決了這條路（「不用為每個服務開一個新 port」），理由充分：埠號沒有語意、防火牆規則會爆炸、要記一堆數字。**不採用。**

---

## 決策

**採用選項 B，子網域路由。**

關鍵理由是**時機**：現在只有一個服務，遷移成本最低。等裝了十個服務再改，就是十倍的工，而且那時每個服務都已經有人在用、有書籤、有設定檔指向舊網址。

> 這是一個常見的架構判斷模式：**當一個決定的「改變成本」會隨時間快速上升時，就要提早決定。** 相對地，改變成本低的決定可以晚點再說（例如要不要加 TLS，隨時可以加）。

---

## 實作計畫

1. ✅ 在 `90` 上安裝 **dnsmasq**，提供區網 DNS
2. ✅ 加入解析紀錄：`grafana.liyibass.internal` → **`192.168.10.90`**
3. ✅ 改寫 Nginx，從 `location` 分流改為 `server_name` 分流
4. ✅ 移除 Grafana 的 `serve_from_sub_path=true`（不再需要）
5. ✅ 讓區網裝置使用 `90` 當 DNS（路由器 DHCP 下發，主要 `192.168.10.90`、次要留空）

> ⚠️ **第 2 步曾經寫錯，值得記下來。**
> 本文原先寫「`grafana.liyibass.internal` → `192.168.10.98`」——**指向後端機器是錯的**。
>
> 服務名稱必須指向 **`192.168.10.90`（反向代理）**。流量要先進 nginx，
> 才輪得到它依 `server_name` 分流。若 DNS 直接指向 98：
> - 瀏覽器會繞過反向代理，這個架構就失去意義
> - 還得自己在網址列打 `:3000`，因為沒有東西幫你轉埠
> - 未來要加 TLS、存取控制、統一日誌時，全部沒有著力點
>
> 直覺上會覺得「名字就該指向那個服務真正住的地方」，但在反向代理架構下，
> **對外的門牌號碼是代理的位址，不是後端的位址**。

### 網域怎麼選？

| 域名 | 問題 |
|---|---|
| `.local` | ❌ 被 mDNS（Bonjour / Avahi）保留，會跟 Apple 裝置打架 |
| `.lan`、`.home` | ⚠️ 沒有正式標準，未來有機會變成真實的頂級域名 |
| `.dev`、`.app` | ❌ **是真的頂級域名**，而且被 Google 強制 HTTPS，區網用會出事 |
| `.home.arpa` | ✅ RFC 8375 保留給家用網路，永遠不會跟公網衝突 |
| **`.internal`** | ✅ **ICANN 於 2024 年保留給私有網路 ← 最終採用** |

> 用 `.dev` 當本機開發域名曾經是常見做法，直到 Google 買下 `.dev` 並加入 HSTS preload 清單——全世界的 `.dev` 一夜之間被瀏覽器強制導向 HTTPS，無數開發環境當場爆炸。**這就是為什麼要用有標準保障的保留域名。**

> **2026-08-01 補充：最初實作用的是 `.home.arpa`，同日稍後改為 `.liyibass.internal`。**
>
> 兩者的保障等價（都是標準明文規定永不委派，性質等同 `192.168.x.x` 之於 IP），
> 改用 `.internal` 純粹是可讀性——它允許在中間放自己的識別，
> `grafana.liyibass.internal` 比 `grafana.home.arpa` 一看就知道是誰的。
>
> 遷移採**新舊並存**：dnsmasq 兩組 `host-record`、nginx 的 `server_name` 列兩個名字，
> 所以套用時機完全不影響服務。確認無人使用舊名稱後再移除。

## 後果

### 正面

- 之後每加一個服務，Nginx 設定是複製貼上改兩個字，不用研究 sub-path 相容性
- 網址可讀性大幅提升
- 為未來的 TLS（每個子網域一張憑證，或一張萬用憑證）鋪好路

### 負面（誠實記錄）

- **多一個單點故障**：dnsmasq 掛了，所有服務都用不了名字。緩解方式是保留 IP 直連當備援（`http://192.168.10.98:3000/`）。

- **nginx 現在會等 dnsmasq 才啟動**（2026-08-01 重開機後實測發現）：

  ```
  nginx.service +67ms
  └─nss-lookup.target @4.633s
    └─dnsmasq.service @4.370s +262ms      ← 裝 dnsmasq 之前沒有這一層
      └─network-online.target @4.347s
  ```

  dnsmasq 提供 `nss-lookup.target`，而 nginx 會等這個 target。兩個服務在同一台機器上，
  現在有了啟動順序的依賴。目前開銷只有 262ms，但**萬一 dnsmasq 啟動失敗，nginx 也會被卡住**。

  > 這是「加服務就是加依賴」的實例。加之前不會有人提醒你，通常出事才發現。
  > 裝完新服務後跑一次 `systemd-analyze critical-chain`，看它有沒有插進別人的路徑上。
- **依賴路由器設定**：要讓所有裝置自動用 `90` 當 DNS，得改路由器的 DHCP 設定。如果路由器不支援，就得每台裝置手動設定——這會是這個方案最大的實務阻力。
- **`90` 的角色變重了**：它從「只轉發流量」變成「還負責名字解析」。這台機器的重要性上升，也讓「它走 WiFi」這件事更值得擔心（見 [ADR-003](ADR-003-網路介面與IP規劃.md)）。

## 已驗證（2026-08-01，路由器：TP-Link Archer BE230）

- [x] 路由器**不支援**自訂 DNS 記錄。全機 DNS 相關設定只有四類：上游 DNS 指定（含 DoH/DoT）、DHCP 下發的 DNS、DDNS（公網 IP → 外網主機名，方向相反）、VPN/IPv6 的 DNS 欄位。**沒有 hosts、沒有 local domain、沒有 static entry。**
      → 原本猜「如果路由器支援可能根本不用裝 dnsmasq」，**這條路走不通**，dnsmasq 確定要裝。

- [x] DHCP **可以**指定 DNS 伺服器。位置：進階 > 網路 > DHCP 伺服器 > 主要 DNS / 次要 DNS（選填，預設空白，空白時下發 `192.168.10.1`）。
      → 第 5 步可自動化，不需逐台手設。

> 💡 TP-Link 家用韌體本來就不提供這個功能——那是 OpenWrt、pfSense、AdGuard Home 那一掛的領域。
> 有趣的是，**多數家用路由器內部跑的就是 dnsmasq**，只是韌體沒把設定介面開放出來。
> 所以我們做的事本質上是：在 90 上跑一個功能完整的版本，取代路由器閹割過的那個。

### ⚠️ 設定時的陷阱：次要 DNS 絕對不要填公共 DNS

直覺會想寫「主要 = `192.168.10.90`，次要 = `8.8.8.8` 當備援」。**不要這樣做**，這會製造間歇性故障。

原因是：**DNS 客戶端不保證「主要失敗才問次要」**。不少作業系統（含 macOS / iOS）會並行查詢，或在主要回應較慢時直接改問次要。只要有一次查詢跑到 `8.8.8.8`，`grafana.liyibass.internal` 就是 NXDOMAIN——症狀是**時好時壞、重試一次又好了**，屬於最難查的那一類故障。

正確做法：**次要留空**，或同樣填 `192.168.10.90`。公網名稱的解析交給 dnsmasq 自己往上游轉發（已設定 `192.168.10.1` + `1.1.1.1`）。

> 這讓「dnsmasq 掛掉」的後果從「名字失效」升級成「連公網 DNS 也斷」。
> 這是這個方案最實質的代價，備援方式仍是 IP 直連（`http://192.168.10.98:3000/`）。

### 實測結果

- [x] **手機實測可正常解析 `.liyibass.internal`** —— 至此整條鏈路（DHCP 下發 DNS →
      dnsmasq 回答 → nginx 依 `server_name` 分流 → Grafana）在真實裝置上驗證完畢。
- [ ] 尚未特別測試**連在 EasyMesh 子節點上**的裝置。這種拓樸偶爾會有子節點自己攔截
      DNS 的行為，若某台裝置解析不到，先確認它連的是主路由器還是子節點。
