# [E-10-10] 數位簽章入門：怎麼確認「這真的是對方發的、而且沒被改過」

> **目標**：理解數位簽章（digital signature）在解決什麼問題——驗證一則訊息的「來源」與「完整性」；搞懂 HMAC（對稱）和非對稱簽章（RSA／Ed25519）差在哪、什麼時候用哪個；並釐清一個最常被搞混的觀念：**簽章不等於加密**。

## 一個問題：你收到一通「銀行打來」的電話

想像你接到一通電話，對方說自己是銀行客服，要你「配合做一筆操作」。你心裡冒出兩個疑問：

1. **這真的是銀行打來的嗎？**（來源對不對）
2. **對方講的內容，中途有沒有被人掉包？**（內容有沒有被動過）

電話很難回答這兩個問題——你聽到的只是一個聲音。但在程式的世界裡，我們常常要替「收到的一則訊息」回答一模一樣的兩個問題。

最典型的場景是 **webhook（網路回呼）**——你的後端服務向某個外部服務註冊了一個網址，當對方那邊發生事件（例如一筆款項完成、一張工單更新），它就主動「打」一個 HTTP 請求到你的網址通知你。問題來了：

```
你的服務收到一個 POST 請求，內容寫著「訂單 A1001 已付款」。

但這個請求，真的是你信任的那個外部服務發來的嗎？
還是某個知道你網址的人，自己偽造了一個「已付款」丟進來？
中途有沒有被人把「訂單 A1001」改成「訂單 A9999」？
```

你的網址是公開的 HTTP 端點，任何人都能往那裡送請求。光靠「收到了一個格式正確的請求」，完全無法證明它可信。這篇要講的**數位簽章**，就是用來回答這兩個問題的工具。

## 生活類比：火漆封印的信

回到還在用信件的年代。一位貴族寄出一封重要的信，他會在信封封口滴上一坨熱蠟，趁蠟還軟的時候用他**專屬的印章**壓上去，留下一個圖案。這叫火漆封印（wax seal）。

收信人看到這個封印，能同時確認兩件事：

- **來源**：這個圖案是那位貴族獨有的印章壓出來的，別人仿不出來 → 信確實是他寄的。
- **完整性**：封印是完整的、沒有被撬開過的痕跡 → 信在路上沒有被人拆開改內容。

數位簽章做的就是同一件事，只是把「蠟」換成數學運算：

> **寄件方用只有自己能用的「密鑰」，對訊息內容算出一小段「簽章」附在訊息旁邊。收件方可以驗證這段簽章，確認（1）訊息確實出自持有那把密鑰的人，（2）訊息內容一個字都沒被改過。**

注意一個關鍵：火漆封印**保護的是「信有沒有被動過、是不是他寄的」，而不是「把信的內容藏起來」**——任何攔截信件的人還是讀得到信裡寫什麼。數位簽章也一樣，這點等一下會特別強調。

## 簽章不等於加密

這是整篇最重要、也最多人搞錯的一句話，先講清楚：

| | 它保護什麼 | 它不保護什麼 |
|---|---|---|
| **加密（encryption）** | **機密性**——讓第三方看不懂內容 | 不保證內容沒被人替換成另一段合法的密文 |
| **簽章（signature）** | **完整性＋來源**——內容有沒有被改、是不是對方發的 | **不保證機密**——簽章不會把原文藏起來，內容照樣看得到 |

換句話說：

- 一則**被簽章**的訊息，內容是**明擺著給大家看的**，只是附帶一張「這是真品、沒被動過」的證明。
- 一則**被加密**的訊息，內容是看不懂的亂碼，但光加密不保證它是誰發的、有沒有被掉包。

兩者解決的是不同問題，常常一起用（例如 HTTPS 底下的 TLS 同時做了加密與身分驗證），但**別把「我有簽章」當成「我的內容很安全不會被看到」**。webhook 的內容本來就是要給你讀的，我們要的從來不是把它藏起來，而是確認它可信。

> 加密與身分驗證在傳輸層怎麼合作 → [E-3-2 HTTPS 與 TLS](../E-3-network/E-3-2-https-tls.md)

## 兩種簽章：對稱（HMAC）與非對稱

數位簽章有兩大流派，差別在「簽的人和驗的人，用的是不是同一把鑰匙」。

### 先看對稱：HMAC

**HMAC（Hash-based Message Authentication Code，雜湊訊息驗證碼）** 的做法是：**簽的人和驗的人，事先共享同一把密鑰（secret key）。** 兩邊都拿這把一樣的鑰匙，對訊息算出一段雜湊，就得到簽章。

用 pseudo code 描述：

```
寄件方（持有密鑰 K）：
    簽章 = HMAC(密鑰 K, 訊息內容)
    把「訊息內容 + 簽章」一起送出

收件方（也持有同一把密鑰 K）：
    自己算一次 = HMAC(密鑰 K, 收到的訊息內容)
    如果 自己算的 == 收到的簽章 → 可信
    否則 → 來源不對，或內容被改過，拒收
```

因為收件方用**一樣的鑰匙**重算一次就能比對，所以叫「對稱」。它的前提是：**這把密鑰只有可信的雙方知道。** 任何拿到這把鑰匙的人，既能簽、也能驗——簽和驗的能力綁在同一把鑰匙上。

### 再看非對稱：RSA／Ed25519

**非對稱簽章**用的是一對數學上配對的鑰匙：**私鑰（private key）** 和 **公鑰（public key）**。

- **私鑰**：只有寄件方自己持有，用來「**簽**」。絕不外流。
- **公鑰**：可以大方公開給任何人，用來「**驗**」。

關鍵特性：**私鑰簽出來的東西，只有對應的公鑰驗得過；而拿到公鑰的人，只能驗、沒辦法反推出私鑰、也沒辦法偽造出新的簽章。** 常見的演算法有 **RSA** 和 **Ed25519**（一種較新、較快、金鑰較短的橢圓曲線簽章演算法）。

```
寄件方（持有私鑰）：
    簽章 = 用私鑰簽(訊息內容)
    把「訊息內容 + 簽章」一起送出

收件方（只需要公鑰，公鑰是公開的）：
    用公鑰驗(訊息內容, 簽章)
    通過 → 確定是私鑰持有者發的、且內容沒被改
    不通過 → 拒收
```

這張圖把兩種流派的「誰拿什麼鑰匙」擺在一起對照：

```mermaid
graph TB
    subgraph HMAC 對稱
        A1["寄件方<br/>持有密鑰 K"] -->|用 K 簽| A2["訊息＋簽章"]
        A2 -->|用同一把 K 驗| A3["收件方<br/>也持有密鑰 K"]
    end
    subgraph 非對稱 RSA／Ed25519
        B1["寄件方<br/>持有私鑰（不外流）"] -->|用私鑰簽| B2["訊息＋簽章"]
        B2 -->|用公鑰驗| B3["收件方<br/>只需要公鑰（可公開）"]
    end
```

這張圖表達：HMAC 兩端共用同一把密鑰，簽與驗是同一把鑰匙的兩種用途；非對稱則把能力拆開——私鑰只給簽，公鑰只給驗，而且公鑰可以公開發給所有人。

### 什麼時候用哪個？

這是實務上真正要做的決定。判準其實很直覺——**驗的那一方，該不該擁有「也能簽」的能力？**

| 情境 | 選哪個 | 為什麼 |
|---|---|---|
| **內部服務彼此互信**（你自家的 A 服務呼叫 B 服務） | **HMAC** | 兩邊都是你的、都信得過，共享一把密鑰最簡單；對方拿到密鑰能驗也能簽，沒關係——反正都是自己人 |
| **對外的第三方 / webhook 驗證**（外部服務通知你、或你發通知給很多客戶） | **非對稱** | 你只想讓對方「**能驗、不能冒充你簽**」。把公鑰發出去，誰都能驗證你發的訊息是真的，但沒有人（包括收件方）能偽造出一則「看起來像你簽的」訊息 |

一句話記法：**共享密鑰（HMAC）= 「我們是自己人，給你一把一樣的鑰匙」；私鑰公鑰（非對稱）= 「我只給你一把『驗證專用』的鑰匙，簽名的能力留在我手上」。**

## 正式程式碼範例

情境：**你收到一個 webhook 請求，要驗證它真的來自你信任的外部服務。** 我們分別用兩種方式寫，都用 Node.js 內建的 `crypto` 模組（不需要額外套件）。

### 方式一：HMAC（雙方共享密鑰）

先看寄件端怎麼產生簽章。這段的作用是：**拿共享密鑰，對請求本文（request body）算出一段 HMAC，之後會放進 HTTP header 送出。**

```typescript
import { createHmac } from "node:crypto";

// 共享密鑰：只有可信的雙方知道，絕不寫死在程式碼或 commit 進 repo（見 E-10-13）
function signWithHmac(requestBody: string, sharedSecret: string): string {
  // 對 request body 算 SHA-256 的 HMAC，輸出成 16 進位字串
  return createHmac("sha256", sharedSecret).update(requestBody).digest("hex");
}
```

接著是收件端的驗證。這段的作用是：**用同一把密鑰自己重算一次簽章，再跟請求帶來的簽章比對；比對要用「定時比較」避免時序攻擊。**

```typescript
import { createHmac, timingSafeEqual } from "node:crypto";

function verifyHmac(
  requestBody: string,
  receivedSignature: string,
  sharedSecret: string,
): boolean {
  // 用一樣的密鑰、一樣的演算法，自己重算一次
  const expected = createHmac("sha256", sharedSecret).update(requestBody).digest("hex");

  const expectedBuffer = Buffer.from(expected, "hex");
  const receivedBuffer = Buffer.from(receivedSignature, "hex");

  // 長度不同直接判定不符（timingSafeEqual 要求兩邊等長）
  if (expectedBuffer.length !== receivedBuffer.length) {
    return false;
  }

  // 不可以用 === 直接比字串：那會「比到第一個不同的字元就回傳」，
  // 攻擊者能從「拒絕所花的時間」一個字元一個字元猜出正確簽章（timing attack，時序攻擊）。
  // timingSafeEqual 不論內容差在哪，都花一樣的時間比完。
  return timingSafeEqual(expectedBuffer, receivedBuffer);
}
```

### 方式二：非對稱（私鑰簽、公鑰驗）

這段的作用是：**寄件端用私鑰對請求本文簽章。** 這裡用 Ed25519，因為它金鑰短、速度快，且不像 RSA 需要額外挑填充（padding）參數。

```typescript
import { sign } from "node:crypto";
import type { KeyObject } from "node:crypto";

// privateKey 由寄件方保管，絕不外流
function signWithEd25519(requestBody: string, privateKey: KeyObject): string {
  // Ed25519 的演算法參數傳 null（它的雜湊方式已內建）
  const signature = sign(null, Buffer.from(requestBody), privateKey);
  return signature.toString("base64");
}
```

這段的作用是：**收件端只用公鑰驗證，不需要、也拿不到私鑰。** 這正是非對稱的好處——驗證方永遠無法反過來偽造簽章。

```typescript
import { verify } from "node:crypto";
import type { KeyObject } from "node:crypto";

// publicKey 是公開的，誰都能拿來驗
function verifyEd25519(
  requestBody: string,
  receivedSignatureBase64: string,
  publicKey: KeyObject,
): boolean {
  return verify(
    null,
    Buffer.from(requestBody),
    publicKey,
    Buffer.from(receivedSignatureBase64, "base64"),
  );
}
```

兩段放在一起看，就能體會差別：HMAC 的 `verify` 需要跟 `sign` **一模一樣的那把密鑰**；Ed25519 的 `verify` 只需要**公鑰**，驗證方就算把程式碼整個外洩，也沒有人能靠它偽造出你的簽章。

## 常見錯誤（反模式）

> **常見錯誤一：以為「有簽章」就等於「內容是加密的、看不到」**
>
> 最常見的誤解。有人在 webhook 加了 HMAC 簽章之後，就把「訂單金額、使用者 email」等敏感內容直接明文塞在請求本文裡，覺得「反正有簽章，安全」。
>
> 問題是：**簽章只證明「內容沒被改、是對方發的」，完全沒有把內容藏起來。** 任何在傳輸途中攔截到這個請求的人，照樣讀得到裡面所有明文。
>
> **正確做法**：機密性要靠「加密」處理——實務上就是**整條連線走 HTTPS（TLS）**，讓內容在傳輸途中是加密的。簽章負責「真不真」，加密負責「看不看得到」，兩件事分開想，該有的都要有。

> **常見錯誤二：對外 webhook 用 HMAC，卻把同一把密鑰發給一大堆第三方**
>
> 你要通知 50 個客戶的系統，為了省事，用一把共享密鑰做 HMAC，然後把這把密鑰發給全部 50 家。
>
> 問題是：**HMAC 的密鑰「能驗也能簽」。** 任何一家客戶（或哪家客戶不小心把密鑰外洩了），都能拿這把密鑰**偽造出「看起來像你發的」通知**丟給其他 49 家。你等於把「冒充自己」的能力親手發了出去。
>
> **正確做法**：對「不完全互信的外部對象」廣播通知時，用**非對稱簽章**——你用私鑰簽，把公鑰發給所有客戶。他們只能驗、不能簽，誰都冒充不了你。HMAC 留給「雙方都是自己人、互相信任」的內部服務。

> **常見錯誤三：驗簽章時用 `===` 直接比字串**
>
> ```typescript
> // ❌ 危險：字串比較「比到第一個不同就回傳」，所花時間會洩漏資訊
> if (receivedSignature === expectedSignature) { /* 通過 */ }
> ```
>
> 問題是：`===` 比較字串時，只要比到第一個不相同的字元就會立刻回傳。攻擊者可以反覆送出猜測的簽章，**從「被拒絕所花的時間長短」反推出自己猜對了前幾個字元**，進而一個字元一個字元把正確簽章試出來——這叫**時序攻擊（timing attack）**。
>
> **正確做法**：用**定時比較（constant-time comparison）**，例如上面範例的 `crypto.timingSafeEqual`。它不論兩邊差在哪個位置，都花一樣的時間比完，不洩漏任何「比到哪裡」的資訊。

## 小結

- **數位簽章**回答兩個問題：這則訊息**是不是對方發的（來源）**、**內容有沒有被改過（完整性）**。典型場景就是驗證「收到的 webhook 真的來自某服務」。
- **簽章 ≠ 加密**：簽章保「完整性＋來源」，**不保機密**——被簽的內容照樣看得到。要藏內容得另外靠加密（HTTPS／TLS）。
- **HMAC（對稱）**：雙方共享同一把密鑰，能簽也能驗。適合**互相信任的內部服務**。
- **非對稱（RSA／Ed25519）**：私鑰簽、公鑰驗，公鑰可公開，驗的人無法偽造。適合**對外第三方 / webhook**——只給對方「驗」的能力，不交出「冒充你簽」的能力。
- 選擇判準一句話：**驗的那方該不該也能簽？能 → HMAC；不能 → 非對稱。**
- 實作細節：驗簽章一定要用**定時比較**，別用 `===`，否則有時序攻擊風險。
