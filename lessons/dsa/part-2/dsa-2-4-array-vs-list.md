# [dsa-2-4] 陣列 vs 鏈結串列：什麼情境用哪個（一張對照表）

> **本章目標**：把陣列和鏈結串列做一次完整對比，建立「拿到需求怎麼選」的判斷力，並認識「快取友善」這個常被忽略的實務因素。

## 你會學到

- 陣列與鏈結串列的完整複雜度對照
- 「快取友善」為什麼讓陣列實務上常勝出
- 怎麼根據「主要操作」選對結構
- 一個務實的建議

## 概念說明

### 完整對照表

把 [dsa-2-1]~[dsa-2-3] 整理成一張總表：

| 操作 | 陣列（動態）| 鏈結串列 |
|------|------|---------|
| 用索引存取第 i 個 | **O(1)** ✅ | O(n) |
| 在結尾插入 | O(1) 攤銷 | O(1)（有尾指標）|
| 在開頭插入/刪除 | O(n) | **O(1)** ✅ |
| 在中間（已知節點）插入/刪除 | O(n) | **O(1)** ✅ |
| 搜尋某個值 | O(n) | O(n) |
| 記憶體 | 連續、緊湊 | 分散、每個節點多存指標 |

```mermaid
graph TB
    ARR["陣列 擅長<br/>✅ 隨機存取 O(1)<br/>✅ 記憶體緊湊、快取友善"]
    LL["鏈結串列 擅長<br/>✅ 開頭/中間增刪 O(1)<br/>✅ 不用預留/擴容"]
```

這張圖總結：**陣列贏在「隨機存取」與「記憶體效率」，鏈結串列贏在「任意位置增刪」。** 它們是互補的一對。

### 一個常被忽略的關鍵：快取友善

理論上鏈結串列「增刪 O(1)」聽起來很美，但**實務上陣列常常更快**——即使在某些理論上鏈結串列佔優的場景。為什麼？因為**快取友善（cache-friendly）**：

```
回憶 cs 課程 Part 3-4 的記憶體階層與「局部性」：
   陣列：元素「連續」存放 → CPU 一次載入一塊，附近元素都進快取
        → 走訪陣列超快（大多在快取命中）
   鏈結串列：節點「散落」各處 → 每跳一個節點可能就要去慢的主記憶體拿
        → 走訪時頻繁 cache miss，實際上慢很多

→ 所以「理論複雜度一樣 O(n) 的走訪」，陣列實務上往往快好幾倍。
  這是純看 Big-O 看不出來的「常數因素」（呼應 dsa-1-1 提的常數）。
```

這是個重要的實務教訓——**Big-O 是第一層篩選，但不是全部**。記憶體存取模式（快取友善）這類「常數因素」，在真實效能裡可能很關鍵。

### 怎麼選

```mermaid
graph TB
    Q["你最常做的操作是？"]
    Q -->|"靠索引讀取、走訪"| ARR["用陣列<br/>(存取快 + 快取友善)"]
    Q -->|"頻繁在開頭/中間增刪<br/>且持有節點參考"| LL["用鏈結串列"]
    Q -->|"不確定 / 一般情況"| ARR2["預設用陣列<br/>(實務上最常見、通常夠好)"]
```

這張圖給選擇建議。注意最後一條——**不確定時，預設用陣列（動態陣列）**。原因：

```
務實的建議：
   現代語言的「動態陣列」（TypeScript 陣列、rust Vec）
   是日常 90% 情況的好選擇——存取快、快取友善、API 方便。
   鏈結串列雖然「某些操作理論上更快」，但快取不友善 + 實作較煩，
   實務上純鏈結串列用得比你想像的少。
   → 除非你「明確知道」需要鏈結串列的特性，否則先用陣列。
```

這呼應 [dsa-0-3] 的「夠好往往勝過最佳」——別過度設計，先用最通用、最不易錯的。

## 範例：兩個情境的選擇

```
情境 A：一個排行榜，要常常「顯示第 N 名」「依分數排序」
   → 主要是「索引存取」和「排序」 → 陣列（存取 O(1)、好排序）

情境 B：實作一個「待處理任務佇列」，常在「頭部移除、尾部加入」
   → 主要是兩端增刪 → 鏈結串列適合（兩端 O(1)）
   → 但其實！用「動態陣列 + 一些技巧」或語言內建的雙端佇列
     往往更實際（快取友善）。下一章的佇列會談到。

→ 重點：先看「主要操作」，再參考「快取友善」與「實作複雜度」綜合判斷。
```

<details>
<summary>參考解答</summary>

**第 1 題：憑記憶填複雜度**

| 操作 | 陣列（動態）| 鏈結串列 |
|------|------|---------|
| 用索引存取第 i 個 | **O(1)** | **O(n)** |
| 在開頭插入/刪除 | **O(n)** | **O(1)** |

記憶法：兩者幾乎「剛好相反」——陣列贏在「索引存取」，鏈結串列贏在「開頭（兩端）增刪」。想不起來時，回到本質：陣列「連續、能算位址」→ 存取快、挪動慢；鏈結串列「散落、靠指標」→ 存取慢、改箭頭快。

**第 2 題：什麼是「快取友善」？為什麼讓陣列實務上更快？**

CPU 從主記憶體拿資料很慢，所以中間有一層很快的「快取（cache）」。CPU 每次讀取，不是只搬一個值，而是**一次搬「一整塊連續的記憶體」進快取**（因為程式通常會用到附近的資料，這叫「局部性」）。

- **陣列**：元素連續存放，CPU 搬一塊進快取時，**附近的元素也順便一起進來了**。接下來走訪這些元素幾乎都在快取裡命中（快），很少要去慢的主記憶體。→ 快取友善。
- **鏈結串列**：節點散落在記憶體各處，每跳一個 `next` 可能就落到「不在快取裡的另一塊記憶體」，於是頻繁 cache miss、被迫去慢的主記憶體拿。→ 快取不友善。

所以就算「走訪」理論上兩者都是 O(n)，實務上陣列往往快好幾倍。這是 Big-O 看不出來的「常數因素」（[dsa-1-1]）——**Big-O 一樣，不代表實際速度一樣。**

**第 3 題（思考題）：為什麼「不確定時預設用陣列」？呼應哪個觀念？**

原因：

1. **實務綜合表現最好**：動態陣列存取快、又快取友善，涵蓋日常約 90% 的情境。
2. **鏈結串列的理論優勢常被快取抵銷**：它「某些操作理論上更快」，但快取不友善 + 實作較繁瑣，真實效能常不如預期。
3. **最不容易出錯、API 最方便**：語言內建、大家熟、踩坑少。

這呼應 [dsa-0-3] 的 **「夠好往往勝過最佳」**（以及「別過度設計」）。與其為了理論上的最佳去挑一個複雜、易錯、實務未必更快的結構，不如先用最通用、最穩、通常「夠好」的陣列——**除非你明確知道自己需要鏈結串列的特性，才特地換掉。**
