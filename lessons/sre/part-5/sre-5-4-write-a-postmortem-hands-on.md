# [sre-5-4] 🔧 動手做：寫一份完整的 postmortem

> **本章目標**：針對一個（真實或模擬的）事故，親手寫一份符合「無咎」精神、結構完整的 postmortem，把 Part 5 的原則化為實際產出。

## 你會學到

- 套用 postmortem 的標準結構
- 用 5 Whys 挖出系統層面的根因
- 寫出「對事不對人」的內容
- 訂出具體、可追蹤的行動項目

## 概念說明

### 這一章在做什麼

Part 5-1~5-3 建立了事故處理與檢討的觀念，這一章你要當一次「postmortem 作者」——拿一個事故，走完整個檢討流程，產出一份真正可用的報告。

postmortem 的價值不在「寫完歸檔」，而在「**讓組織真的學到、真的改善**」。所以重點是後半段的「根因」和「行動項目」。

我們用一個具體的模擬事故來示範。

## 範例：一份完整的 postmortem

假想事故：**「某天晚間，購物網站結帳功能中斷約 25 分鐘」**。下面是一份完整的 postmortem 範本，你可以照這個格式寫自己的。

```markdown
# Postmortem：結帳服務中斷（2026-06-15）

## 摘要
2026-06-15 20:14–20:39（約 25 分鐘），結帳服務無法使用，
約 3,200 名使用者無法完成結帳。透過回滾止血後恢復。

## 影響
- 受影響使用者：約 3,200 人無法結帳
- 預估損失營收：約 NT$180,000
- SLO 影響：本月錯誤預算消耗約 40%
- 嚴重程度：高（核心營收功能中斷）

## 時間軸（依 5-2 的事故記錄整理）
- 20:10  部署結帳服務新版本 v2.4
- 20:14  🔔 告警：結帳錯誤率 > 1% 持續 5 分鐘（Part 4 的症狀告警生效）
- 20:16  on-call 確認為真實事故，宣告事故、進事故頻道
- 20:20  懷疑與 20:10 的部署有關
- 20:24  ✅ 決定回滾到 v2.3（止血優先，不先查 bug，Part 5-1）
- 20:28  回滾完成
- 20:39  確認錯誤率恢復正常、使用者能結帳，事故解除
- 21:30  在測試環境重現，找到根因

## 根本原因（用 5 Whys 往下挖，Part 5-3）
結帳失敗。
  為什麼？→ v2.4 呼叫金流 API 時拋出未處理的例外。
  為什麼會拋例外？→ 新版本改了金流回應的解析，沒處理「金流逾時」的情況。
  為什麼沒測到？→ 測試只涵蓋「金流正常回應」，沒測「逾時」情境。
  為什麼漏了這個測試？→ 沒有「外部依賴失敗」的測試規範。
  
根本原因（對事不對人）：
  測試流程缺乏「外部依賴失敗情境」的覆蓋，
  使得「金流逾時」這個未處理路徑進到了正式環境。

## 偵測與處理檢討
- 偵測：✅ 症狀告警 4 分鐘內就響，表現良好
- 止血：✅ 6 分鐘內決定回滾，快速止血
- 可改善：回滾流程是手動的，花了 4 分鐘，可以更快

## 行動項目（最重要，Part 5-5）
1. [ ] 為金流串接補上「逾時/失敗」情境的測試（負責人：A，期限：2026-06-22）
2. [ ] 建立「外部依賴失敗」的測試規範（負責人：B，期限：2026-06-30）
3. [ ] 把回滾流程自動化，縮短止血時間（負責人：C，期限：2026-07-15）
4. [ ] 結帳程式為所有外部呼叫加上逾時處理（負責人：A，期限：2026-06-29）

## 學到的教訓
- 「外部依賴會失敗」必須在設計與測試時就考慮（呼應 Part 8 為失敗而設計）
- 症狀告警與快速回滾的機制運作良好，要保持
```

### 寫作時的檢查點

對照你寫的內容，確認：

- [ ] **時間軸**清楚（沒有時間軸的 postmortem 是空談）
- [ ] **根因**挖到系統層面（用了 5 Whys，沒停在表面）
- [ ] 全程**對事不對人**（沒有出現「某某人粗心」這種句子）
- [ ] **行動項目**具體（有負責人、有期限、可追蹤——不是「以後要更小心」這種空話）
- [ ] 誠實面對「哪裡可以更好」

最關鍵的是**行動項目**——它是 postmortem 唯一會「改變未來」的部分。下一章 5-5 專門講怎麼讓這些行動項目真的被執行，而不是寫完就忘。

## 小練習

### 練習 1：寫一份 postmortem

挑一個事故來寫——可以是：

- 你（或你聽說過的）真實遇過的線上事故
- 或一個模擬事故（例如「資料庫磁碟滿了導致服務中斷」）

照本章的結構，寫出完整的 postmortem。

<details>
<summary>參考解答</summary>

以「資料庫磁碟滿了導致服務中斷」為例，套用本章結構的示範：

```markdown
# Postmortem：資料庫磁碟寫滿導致服務中斷（2026-07-03）

## 摘要
2026-07-03 02:10–03:05（約 55 分鐘），主資料庫磁碟寫滿，
所有寫入操作失敗，使用者無法下單、無法更新資料。清理日誌與擴充磁碟後恢復。

## 影響
- 受影響使用者：全站寫入功能中斷，約 8,000 名活躍使用者受影響
- SLO 影響：本月可用性錯誤預算消耗約 60%
- 嚴重程度：高（核心寫入功能全面中斷）

## 時間軸（依 5-2 的事故記錄整理）
- 02:10  🔔 告警：資料庫寫入錯誤率飆高
- 02:14  on-call 確認為真實事故，宣告事故、進事故頻道
- 02:22  診斷發現資料庫磁碟使用率 100%
- 02:30  ✅ 止血：清理過期的交易日誌，釋放空間讓寫入恢復
- 02:40  寫入恢復，但空間仍吃緊，決定線上擴充磁碟
- 03:05  磁碟擴充完成、確認一切正常，事故解除

## 根本原因（用 5 Whys 往下挖，Part 5-3）
服務中斷。
  為什麼？→ 資料庫磁碟寫滿，寫入全部失敗。
  為什麼會寫滿？→ 交易日誌持續增長，沒有被清理或輪替。
  為什麼沒被清理？→ 沒有設定日誌自動輪替/清理策略。
  為什麼沒人先發現快滿了？→ 沒有「磁碟使用率」的預警告警，只有事後的錯誤告警。

根本原因（對事不對人）：
  缺乏磁碟容量的預警告警與日誌自動清理機制，
  使得磁碟悄悄漲到 100% 才在「服務已中斷」時被發現。

## 偵測與處理檢討
- 偵測：❌ 只有錯誤發生後才告警，等於出事才知道，可改善
- 止血：✅ 清日誌快速釋放空間，8 分鐘內恢復寫入
- 可改善：磁碟擴充是手動、較慢；應該在「快滿」時就先預警

## 行動項目（最重要，Part 5-5）
1. [ ] 為資料庫磁碟使用率加上「超過 80% 預警」告警（負責人：A，期限：2026-07-10）
2. [ ] 設定交易日誌自動輪替與清理策略（負責人：B，期限：2026-07-17）
3. [ ] 盤查其他伺服器是否也缺磁碟容量告警，一併補上（負責人：C，期限：2026-07-24）

## 學到的教訓
- 容量類問題要「在滿之前預警」，而不是「滿了才用錯誤告警得知」
- 快速止血（清日誌）與根治（自動輪替+預警）要分開看，兩者都要做
```

重點不在文字多漂亮，而在：**時間軸清楚、根因挖到系統層面、全程對事不對人、行動項目具體有主有期。**

</details>

### 練習 2：檢查「對事不對人」

寫完後，重讀你的根因和時間軸，把任何「指向某個人」的句子，改寫成「指向系統缺陷」的句子。

> 例：「值班的人反應太慢」→「缺乏 runbook，使得處理時需要臨場摸索」。

<details>
<summary>參考解答</summary>

作法：逐句掃過根因與時間軸，只要句子的主詞是「某個人」或在暗示「某人的疏失/態度」，就改寫成指向**系統/流程缺陷**的句子。幾個示範：

- 「值班的人反應太慢」 → 「缺乏 runbook，處理時需要臨場摸索，拉長了反應時間」
- 「小明部署前忘了跑測試」 → 「部署流程沒有把測試設為強制關卡，允許未測程式進到正式環境」
- 「工程師打錯指令刪了資料」 → 「正式環境的危險操作缺少二次確認與權限隔離，單一指令即可造成破壞」
- 「客服太晚回報」 → 「缺乏使用者回報快速進到工程團隊的通報管道」
- 「他判斷錯誤選了回滾」 → 「當下缺乏足夠的監控資訊，難以快速判斷正確的止血方向」

判斷訣竅：改寫後問自己——「這句話指到的東西，**修得動嗎？**」指向人的句子（叫他小心、處分他）修不動，因為人還是會犯錯；指向系統的句子（加關卡、加確認、加 runbook、加管道）才是真正能落地改善的。

</details>

### 練習 3：訂出好的行動項目

檢查你的行動項目，每一條是否都「具體、有負責人、有期限、可追蹤」？把任何像「以後要小心」「加強注意」這種空話，改寫成具體可執行的行動。

<details>
<summary>參考解答</summary>

好的行動項目要同時滿足四個條件：**具體（做什麼）、有負責人（誰做）、有期限（何時做完）、可追蹤（進到工作系統，如 Jira / GitHub Issues）。** 空話改寫示範：

- 「以後部署要更小心」 → 「[Jira-XXXX] 在部署流程加入自動化測試強制關卡，未通過不得上正式（負責人：A，期限：7/20）」
- 「加強測試」 → 「[Jira-XXXX] 為金流串接補上『逾時/失敗』情境的測試（負責人：B，期限：7/15）」
- 「加強注意監控」 → 「[Jira-XXXX] 為結帳錯誤率加上超過 1% 持續 5 分鐘的告警（負責人：C，期限：7/18）」

檢查訣竅：每一條唸完後問「**明天有人能直接動手、而且看得出哪天算做完了嗎？**」如果答案模糊（像「以後要小心」），就還是空話。另外別忘了最關鍵的一點——把它們**放進團隊平常在用的工作追蹤系統**，和其他工作一起排優先級、被定期 review；躺在 postmortem 文件裡的行動項目注定被遺忘（這正是下一章 5-5 的主題）。

</details>
