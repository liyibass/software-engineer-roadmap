# [sre-8-3] 冗餘與故障轉移：單點掛掉也不致命

> **本章目標**：複習冗餘的概念（infra Part 9-2），深入「故障轉移」怎麼運作，並理解 Multi-AZ、Multi-Region 這些把「故障影響」隔離開來的設計。

## 你會學到

- 冗餘（Redundancy）與故障轉移（Failover）怎麼配合
- 故障轉移的關鍵：健康檢查 + 自動切換
- Multi-AZ：跨機房的冗餘
- Multi-Region：跨地區的冗餘，以及它的代價

## 概念說明

### 複習：冗餘消除單點故障（infra Part 9-2）

infra Part 9-2 學過：**單點故障（SPOF）** 是「掛了就全完」的環節，而**冗餘（Redundancy）** 是消除它的方法——關鍵環節都準備備份，一個掛了另一個頂上。

這一章從 SRE 角度深入：光有「備份」還不夠，關鍵是**怎麼在故障時自動切換過去**——這就是故障轉移。

---

### 故障轉移（Failover）：怎麼自動切換

**故障轉移（Failover）** 是「**當主要的元件掛掉時，自動切換到備援**」的機制。它需要兩個要素：

```mermaid
graph LR
    HC["① 健康檢查<br/>持續確認『誰還活著』"]
    SW["② 自動切換<br/>偵測到掛掉 → 流量導向健康的"]
    HC --> SW
```

**① 健康檢查（Health Check）**：持續地、自動地確認每個元件「還活著、還健康」。例如負載平衡器每幾秒對每台後端發一個健康檢查請求（呼應 infra Part 9-1 Nginx 會跳過壞掉的後端）。

**② 自動切換**：一旦健康檢查發現某個元件掛了，**自動把流量導向健康的備援**，不需要人介入。

關鍵是這整個過程要**快、且自動**——慢了或要人手動切，使用者就會受影響。理想是使用者完全無感（呼應 infra Part 9-2 的「高可用」目標）。

---

### Multi-AZ：跨機房的冗餘

光「同一個機房裡放兩台機器」還不夠——如果**整個機房**出事（斷電、火災、網路中斷）呢？兩台一起掛。

**Multi-AZ** 解決這個。AZ 是 **Availability Zone（可用區）**——可以理解為「**獨立的機房**」，有各自的電力、網路、冷卻。把資源**分散到多個 AZ**，就算一個 AZ 整個掛掉，其他 AZ 的還在。

```mermaid
graph TB
    LB["負載平衡器<br/>（跨 AZ）"]
    LB --> AZ1["可用區 A（機房1）<br/>應用 + 資料庫主節點"]
    LB --> AZ2["可用區 B（機房2）<br/>應用 + 資料庫副本"]
    AZ1 -.->|"AZ-A 整個掛掉"| AZ2
    AZ2 -.->|"故障轉移：副本升為主"| OK["服務繼續"]
```

用類比：別把所有雞蛋放在同一個籃子（機房）——分散到多個籃子，摔破一個還有其他的。

Multi-AZ 是雲端高可用的**標準做法**，而且雲端讓它很容易實現（AWS 課程 Part 4 會深入）。例如 AWS RDS 的「Multi-AZ」選項，會自動在另一個 AZ 維護資料庫副本，主節點掛了自動切換。

---

### Multi-Region：跨地區的冗餘

比 Multi-AZ 更進一步的是 **Multi-Region**——把資源分散到**不同的地理區域**（例如台灣、東京、美國）。

它防範的是「**整個區域級的災難**」：大地震、大範圍斷電、區域性的雲端服務中斷。即使整個「台灣區」都掛了，「東京區」還能服務。

但 Multi-Region 的**代價高很多**：

| 挑戰 | 說明 |
|------|------|
| **資料同步難** | 資料要跨地區複製，物理距離造成延遲，還有「資料一致性」的難題 |
| **複雜度高** | 跨區的流量導向、故障轉移都更複雜 |
| **成本高** | 多個區域的資源都要錢 |

所以 Multi-Region 不是人人都需要——它呼應 Part 1-3「擁抱風險、剛剛好」：**只有「區域級災難真的無法承受」的關鍵服務（如全球金融、大型平台），才值得這個成本。** 大多數服務做好 Multi-AZ 就夠了。

---

### 冗餘也要花成本——回到「剛剛好」

這章要連回 SRE 的核心智慧：**冗餘不是越多越好，要對應你的 SLO 和可承受的風險**。

```
單台          → 便宜，但單點故障（適合：不重要的內部工具）
Multi-AZ      → 防機房級故障，成本適中（適合：大多數正式服務）
Multi-Region  → 防區域級災難，成本高（適合：絕不能停的關鍵服務）
```

選哪一層，取決於「**這個服務掛掉的後果有多嚴重、值不值得那個成本**」——這正是 Part 2 的 SLO 和 Part 1-3 的「擁抱風險」在指導你做決策。

## 範例：依重要性選擇冗餘層級

```
某公司的不同服務，依重要性選不同冗餘：

內部 Wiki：
  → 單一 AZ 就好（掛了員工等一下，影響小，不值得多花錢）

主要的電商網站：
  → Multi-AZ（一個機房掛掉也要能繼續賣，但區域級災難可接受短暫中斷）
  → 資料庫用 Multi-AZ 自動故障轉移

全球金流核心：
  → Multi-Region（這個絕對不能停，區域災難也要扛住）
  → 接受高成本與複雜度，換取最高可靠性

決策依據：每個服務「掛掉的後果」× SLO 要求 → 選對應的冗餘層級
```

注意——**不是全部都上 Multi-Region**。那會浪費大量成本在「其實沒那麼關鍵」的服務上。依 SLO 和後果嚴重性，選「剛剛好」的冗餘——這才是成熟的 SRE 判斷。

## 小練習

### 練習 1：故障轉移的兩要素

回答：故障轉移要能運作，需要哪兩個要素？為什麼這個過程要「快且自動」？

<details>
<summary>參考解答</summary>

**兩個要素：**

1. **健康檢查（Health Check）**：持續地、自動地確認每個元件「還活著、還健康」。例如負載平衡器每隔幾秒對每台後端發一個健康檢查請求，用來判斷「誰還能用、誰掛了」（呼應 infra Part 9-1 Nginx 會跳過壞掉的後端）。這是「偵測故障」的眼睛。
2. **自動切換**：一旦健康檢查發現某個元件掛了，**自動把流量導向健康的備援**，不需要人介入。這是「反應故障」的手。

有偵測（健康檢查）也有反應（自動切換），故障轉移才能成立——只有備份卻沒有這兩者，掛掉時流量仍會打向死掉的節點。

**為什麼要「快且自動」：**

- **要快**：從「元件掛掉」到「流量切到備援」之間的空窗期，使用者是受影響的（請求失敗或延遲飆高）。切得越慢，受影響的時間越長、範圍越大。理想是快到使用者幾乎無感（呼應高可用目標）。
- **要自動**：故障不會挑上班時間發生——很可能在半夜、沒人盯著的時候。如果要靠人手動切換，就得等有人發現、有人上線、有人操作，這期間服務一直是壞的。自動切換才能在故障的瞬間立刻反應，不依賴「剛好有人在」。

一句話：慢了或要靠人，使用者就會實際受影響；快且自動才能把故障影響壓到最小、逼近「使用者無感」。

</details>

### 練習 2：AZ vs Region

用「雞蛋與籃子」的類比，解釋 Multi-AZ 和 Multi-Region 各防範什麼。為什麼大多數服務做 Multi-AZ 就夠，不一定需要 Multi-Region？

<details>
<summary>參考解答</summary>

**雞蛋與籃子的類比：**

- **Multi-AZ**：把雞蛋分放在**同一個房間裡的多個籃子**。AZ（Availability Zone，可用區）就是「獨立的機房」，各有自己的電力、網路、冷卻。Multi-AZ 防範的是**機房級故障**——單一機房斷電、火災、網路中斷時，摔破一個籃子（一個機房），其他籃子裡的雞蛋還在，服務繼續。
- **Multi-Region**：把籃子分放在**不同城市的房子裡**。Region 是不同的地理區域（如台灣、東京、美國）。Multi-Region 防範的是**整個區域級的災難**——大地震、大範圍斷電、區域性的雲端服務中斷。就算整棟房子（整個區域）都毀了，別的城市的籃子還在。

**為什麼大多數服務做 Multi-AZ 就夠：**

1. **常見故障 Multi-AZ 已能覆蓋**：實務上絕大多數的故障是「單台機器掛」或「單一機房出事」——這些 Multi-AZ 都擋得住。真正的「整個區域級災難」很罕見。
2. **Multi-Region 代價高很多**：資料要跨地區複製，物理距離帶來延遲與「資料一致性」難題；跨區的流量導向、故障轉移複雜度大增；多個區域的資源都要付錢，成本高。
3. **要「剛剛好」，不是越多越好**（呼應 Part 1-3 擁抱風險、Part 2 的 SLO）：冗餘要對應「這個服務掛掉的後果有多嚴重、值不值得那個成本」。對大多數服務來說，「區域級災難造成短暫中斷」是可以承受的風險，花大錢上 Multi-Region 去防一個極罕見的災難並不划算。

所以：大多數正式服務做好 Multi-AZ 就達到成本與可靠性的甜蜜點；只有「區域級災難真的無法承受」的關鍵服務（全球金融、大型平台）才值得 Multi-Region 的成本。

</details>

### 練習 3：選擇冗餘層級

幫下面的服務各選一個合理的冗餘層級（單台 / Multi-AZ / Multi-Region）並說明理由：

1. 一個給內部測試用的環境
2. 一個正式的線上購物網站
3. 一個處理全球即時交易的證券系統

<details>
<summary>參考解答</summary>

判斷依據都是同一句話：**「這個服務掛掉的後果有多嚴重 × SLO 要求」→ 選剛剛好的冗餘層級**。

**1. 內部測試環境 → 單台（單一 AZ）就好**

理由：這是給內部用的，掛掉頂多讓工程師等一下重跑，影響小、也不對外、沒有營收或使用者體驗的損失。為它上 Multi-AZ 甚至 Multi-Region 是把錢浪費在「其實沒那麼關鍵」的地方。用最便宜的層級，把預算留給真正重要的服務。

**2. 正式線上購物網站 → Multi-AZ**

理由：這是對外營運、直接關係營收與使用者信任的正式服務，一個機房掛掉也要能繼續賣，所以需要跨機房的冗餘（例如資料庫用 Multi-AZ 自動故障轉移）。但「區域級災難導致短暫中斷」通常是可承受的風險——為了防那個罕見情況去上 Multi-Region，成本與複雜度不划算。Multi-AZ 是這類服務的標準甜蜜點。

**3. 全球即時交易證券系統 → Multi-Region**

理由：這是「絕對不能停」的關鍵服務——即時交易停擺的後果極其嚴重（金錢損失、法規責任、信任崩塌），連區域級災難都必須扛住。這種服務的後果嚴重性與 SLO 要求高到足以正當化 Multi-Region 的高成本與複雜度，用最高等級的冗餘換取最高的可靠性。

重點：**不是全部都上最高層級**。依後果嚴重性與 SLO 選「剛剛好」的冗餘，才是成熟的 SRE 判斷。

</details>
