# [sre-8-4] 安全發布：藍綠、金絲雀、漸進式

> **本章目標**：理解「上線」是事故的最大來源，學會用藍綠部署、金絲雀發布、漸進式 rollout 把「上線」變成低風險的操作。

## 你會學到

- 為什麼「部署/上線」是最常見的事故來源
- 藍綠部署（Blue-Green）：瞬間切換、瞬間回滾
- 金絲雀發布（Canary）：先放一小部分流量試水溫
- 漸進式 rollout 與快速回滾的重要性

## 概念說明

### 殘酷的事實：大部分事故來自「改動」

回想 Part 1-1 那個 Dev 與 Ops 的對立——維運想「少改動」是有道理的，因為：

> **絕大多數的線上事故，是由「改動」造成的——尤其是「部署新版本」。**

系統穩穩跑著好好的，往往是「上線了一個有問題的新版本」之後才爆炸（Part 5-4 那個金流事故就是）。

但我們又不能「不上線」（那就沒有進步，違反 Part 2-4 錯誤預算的精神）。所以 SRE 的答案不是「少上線」，而是——**把「上線」這個動作本身，設計成低風險、可控、可快速回滾的。** 這就是「安全發布」。

---

### 為什麼「一次全部換掉」很危險

最原始的部署方式是「**直接把所有機器的舊版本換成新版本**」。這很危險：

- 如果新版本有問題，**所有使用者立刻全部受影響**（炸全部人）。
- 要回滾也慢——又要把所有機器換回去。

下面三種方法，核心都是**「別一次換全部、別讓所有人同時承受風險」**。

---

### 方法一：藍綠部署（Blue-Green）

準備**兩套一模一樣的環境**：「藍」（目前正在服務的舊版）和「綠」（部署好新版、但還沒接流量）。

```mermaid
graph LR
    LB["流量入口"]
    LB -->|"目前"| BLUE["藍環境（舊版）<br/>正在服務"]
    GREEN["綠環境（新版）<br/>待命，已測試"]
    LB -.->|"切換！瞬間導向綠"| GREEN
```

流程：在「綠」環境部署新版、測試好 → 把流量**瞬間從藍切到綠** → 新版上線。

最大的好處是**回滾極快**：如果綠（新版）出問題，**瞬間把流量切回藍（舊版）就好**——舊環境還完整地在那。回滾從「重新部署」變成「切一下開關」，幾秒搞定（呼應 Part 5-1 的「止血優先、回滾」）。

代價：要維持兩套環境，成本較高。

---

### 方法二：金絲雀發布（Canary）

名字來自礦工的典故——以前礦工帶**金絲雀**下礦坑，金絲雀對毒氣敏感，如果牠出事，礦工就知道該撤了。**金絲雀發布**就是用「一小部分流量」當那隻金絲雀。

```mermaid
graph LR
    LB["流量"]
    LB -->|"95%"| OLD["舊版"]
    LB -->|"5%（金絲雀）"| NEW["新版"]
    NEW -.->|"觀察：新版的錯誤率/延遲正常嗎？"| CHECK{"健康？"}
    CHECK -->|"是 → 逐步加大"| MORE["10% → 50% → 100%"]
    CHECK -->|"否 → 回滾"| ROLLBACK["撤掉新版"]
```

流程：先讓**一小部分流量（如 5%）**走新版，**其餘走舊版** → **盯著新版的監控**（錯誤率、延遲——Part 3 黃金訊號）→ 如果健康，逐步加大（10% → 50% → 100%）；如果出問題，立刻撤掉，**只有那 5% 受影響**。

最大好處：**把「新版出包」的影響，限制在一小部分使用者**。你用 5% 的人試水溫，而不是拿 100% 的人賭。

---

### 方法三：漸進式 rollout

金絲雀的概念延伸——**不要一次部署到所有機器，而是分批慢慢來**：先 1 台、觀察；再 10%、觀察；再 50%；最後 100%。每一批之間都盯著監控，有問題就停。

這和金絲雀的精神一致：**逐步擴大、持續觀察、隨時能停**。差別是金絲雀強調「用流量比例試水溫」，漸進式強調「分批推進」，實務上常結合使用。

---

### 共同的命脈：快速回滾 + 監控

不管用哪種方法，兩件事是安全發布的命脈：

1. **快速回滾**：任何發布都必須「能快速退回上一個正常版本」。回滾是上線時的「安全氣囊」（Part 5-1 最常用的止血手段）。
2. **發布時緊盯監控**：上線過程中，眼睛要盯著黃金訊號（Part 3）。新版讓錯誤率/延遲變差了嗎？這就是「金絲雀健不健康」的判斷依據。理想上甚至能**自動化**——監控偵測到新版指標惡化，自動回滾。

> 這些安全發布手段，通常整合在 CI/CD 流程裡自動執行（AWS 課程 Part 9、infra 的自動化）。SRE 的工作是設計這套「讓上線變安全」的流程。

## 範例：一次金絲雀發布

```
要上線結帳服務的新版 v3.0

① 部署 v3.0，先導 5% 流量過去（金絲雀）
   → 盯著監控：v3.0 的錯誤率、延遲 vs v2.9（舊版）
   
② 觀察 15 分鐘：
   v3.0 錯誤率 0.05%、延遲 p95 180ms → 和舊版一樣健康 ✅
   
③ 逐步加大：5% → 25% → 50%，每階段都觀察
   → 一路正常
   
④ 100%，v3.0 完全上線

────────────────────────────────────
對比：如果 v3.0 有 bug 會怎樣？

直接全量上線：100% 使用者立刻中招 → 大事故
金絲雀發布：只有那 5% 受影響 → 監控發現異常 → 立刻回滾
            → 95% 的使用者全程無感
```

這就是安全發布的價值——**把「上線」這個高風險動作，變成「可控、影響有限、隨時能撤」的操作**。讓你既能快速迭代（Dev 想要的），又不會炸到使用者（Ops 想要的）——完美調和了 Part 1-1 的那個對立。

## 小練習

### 練習 1：為什麼上線要小心

回答：為什麼說「部署新版本」是最常見的事故來源？SRE 的對策是「少上線」嗎？

<details>
<summary>參考解答</summary>

**為什麼「部署新版本」是最常見的事故來源：**

因為**絕大多數線上事故是由「改動」造成的**。系統穩穩跑著往往沒事，一旦上線了一個有問題的新版本（帶著 bug、設定錯誤、沒考慮到的邊界情況），就在「改動」的那一刻爆炸——這也是為什麼維運（Ops）天生想「少改動」是有道理的（Part 1-1 的 Dev/Ops 對立），Part 5-4 那個金流事故正是這樣來的。改動是把「未知」引入穩定系統的動作，風險自然集中在這裡。

**SRE 的對策是「少上線」嗎？不是。**

「少上線」等於不進步，也違反 Part 2-4 錯誤預算的精神（有預算就該拿去換迭代速度）。SRE 的答案不是減少上線次數，而是——**把「上線」這個動作本身，設計成低風險、可控、可快速回滾的操作**。

具體就是這章的安全發布手段：藍綠部署、金絲雀發布、漸進式 rollout，加上「快速回滾 + 緊盯監控」。核心精神是「**別一次換全部、別讓所有人同時承受風險**」，先用一小部分流量/機器試水溫，健康才逐步擴大，出問題立刻回滾。這樣既能快速迭代（Dev 要的），又不會炸到所有使用者（Ops 要的），調和了兩者的對立。

</details>

### 練習 2：三種方法的差別

用一句話分別說明藍綠部署、金絲雀發布、漸進式 rollout 的核心做法。藍綠部署最大的優勢是什麼？

<details>
<summary>參考解答</summary>

**各一句話：**

- **藍綠部署（Blue-Green）**：準備兩套一模一樣的環境（藍＝正在服務的舊版、綠＝部署好待命的新版），在綠測試好後把流量**瞬間從藍切到綠**。
- **金絲雀發布（Canary）**：先讓**一小部分流量（如 5%）**走新版、其餘走舊版，盯著新版的監控（黃金訊號），健康才逐步加大到 100%、出問題就撤。
- **漸進式 rollout**：不一次部署到所有機器，而是**分批推進**（先 1 台 → 10% → 50% → 100%），每批之間盯監控，有問題就停。

**藍綠部署最大的優勢：回滾極快。** 因為舊版（藍）環境還完整地待在那裡，一旦新版（綠）出問題，只要**把流量切回藍就好**——回滾從「重新部署一輪」變成「切一下開關」，幾秒鐘搞定（呼應 Part 5-1 止血優先、回滾）。代價是要同時維持兩套環境、成本較高。

</details>

### 練習 3：設計發布流程

你要上線一個重要功能的新版本。設計一個安全的發布流程：用哪種方法？怎麼觀察？發現問題怎麼辦？

> 提示：結合金絲雀（小流量試水溫）+ 盯黃金訊號 + 快速回滾。

<details>
<summary>參考解答</summary>

以「上線一個重要功能的新版本」為例，設計如下（結合金絲雀 + 監控 + 快速回滾）：

**用哪種方法：以金絲雀發布為主，搭配漸進式 rollout 分批推進。** 重要功能絕不能一次全量上線炸到所有人；先用一小部分流量試水溫最安全。若環境允許，用藍綠部署做底座（讓回滾能秒切回舊版）會更保險。

**發布流程：**

1. **上線前準備**：確認回滾機制可用（藍綠可切、或能一鍵退回上一版），確認監控儀表板就緒（Part 3 黃金訊號：錯誤率、延遲、流量、飽和度），並記下舊版當前的基準值當對照。
2. **金絲雀階段（5%）**：部署新版，只導 5% 流量過去，其餘 95% 仍走舊版。
3. **觀察**：盯著新版的黃金訊號，並和舊版**同時對照**——新版的錯誤率、p95/p99 延遲是否和舊版一樣健康？觀察一段有意義的時間（如 15 分鐘，涵蓋足夠請求量），別急著放大。
4. **逐步放大**：健康就分批加大（5% → 25% → 50% → 100%），**每一階段都重新觀察**，指標一惡化就停在原地不再往上。
5. **發現問題怎麼辦**：只要監控看到新版錯誤率/延遲變差，**立刻回滾**——把流量切回舊版（藍綠秒切，或撤掉金絲雀）。因為問題只影響那一小部分流量，絕大多數使用者全程無感。回滾優先於「現場除錯」（Part 5-1 止血優先）。
6. **理想進階**：把「監控偵測到指標惡化 → 自動回滾」做成自動化，整合進 CI/CD，不用等人半夜盯著。

**核心精神**：用一小部分使用者試水溫、拿黃金訊號當金絲雀健不健康的判準、任何時候都能快速回滾——把高風險的「上線」變成可控、影響有限、隨時能撤的操作。

</details>
