# [sre-8-2] 優雅降級與保命機制：限流與負載卸除

> **本章目標**：學會「過載時怎麼保命」——優雅降級、限流、負載卸除，讓系統在壓力超過極限時「部分服務」而不是「整個崩潰」。

## 你會學到

- 優雅降級（Graceful Degradation）是什麼
- 限流（Rate Limiting）：保護系統不被請求淹沒
- 負載卸除（Load Shedding）：過載時主動丟棄部分請求
- 為什麼「服務 90% 的人」遠勝「0% 的人都不能用」

## 概念說明

### 核心抉擇：崩潰 vs 降級

Part 7-2 的負載測試讓你看過：系統超過極限時，有兩種「死法」：

```mermaid
graph TB
    OVER["流量超過系統極限"]
    OVER --> CRASH["❌ 整個崩潰<br/>所有人都不能用（0%）"]
    OVER --> DEGRADE["✅ 優雅降級<br/>服務大部分人（如 90%）<br/>少數被婉拒"]
```

- **崩潰**：系統被壓垮，**所有人都不能用**。最糟。
- **優雅降級（Graceful Degradation）**：系統主動「**犧牲一部分，保住大部分**」——服務 90% 的人，少數被暫時婉拒或降級體驗。

SRE 的核心智慧：

> **「服務 90% 的使用者」遠勝「系統崩潰、0% 的人能用」。**

過載時，與其「大家一起死」，不如「主動保住大多數」。這就是優雅降級的精神。下面是實現它的幾個機制。

---

### 機制一：優雅降級——關掉次要功能保住核心

當系統壓力大，**主動關閉「次要功能」，把資源留給「核心功能」**。

例如電商在大促爆量時：

- 核心功能（瀏覽、下單、結帳）→ 全力保住。
- 次要功能（個人化推薦、「猜你喜歡」、評論區）→ 暫時關掉或顯示簡化版。

使用者也許注意到「推薦不見了」，但他**還是能買東西**——核心體驗保住了。等流量退去再恢復次要功能。這比「為了顯示推薦，結果整站崩潰、連買都不能買」好太多。

用類比：醫院急診爆滿時，會**檢傷分類**——先救命危的，輕症的等一下。資源有限時，優先保住最重要的。

---

### 機制二：限流（Rate Limiting）——別讓人灌爆你

**限流（Rate Limiting）** 是「**限制每個使用者/來源，在單位時間內能發多少請求**」。超過就婉拒（回傳 429 Too Many Requests）。

它保護系統不被「異常大量的請求」淹沒，來源可能是：

- **惡意攻擊**：有人想用海量請求打垮你（DoS）。
- **失控的程式**：某個客戶端 bug，瘋狂重試（呼應 8-1 沒做好退避的後果）。
- **單一大戶**：某個使用者用量異常大，影響其他人。

用類比：限流像**夜店門口的人數管制**——一次只放一定數量進場，維持裡面的體驗，而不是讓所有人一次擠爆、誰都玩不了。

限流保護的是「**公平**」和「**穩定**」——不讓少數來源吃掉所有資源，保障多數人的體驗。

---

### 機制三：負載卸除（Load Shedding）——過載時主動丟棄

**負載卸除（Load Shedding）** 比限流更激進：當系統**整體**快過載時，**主動丟棄一部分請求**，保住處理其他請求的能力。

差別：

- **限流**：針對「單一來源」設上限（你發太多，擋你）。
- **負載卸除**：針對「系統整體」——當整體要撐不住了，**犧牲一部分請求**（可能依優先級丟棄），確保剩下的能被好好處理。

用類比：負載卸除像**超載的救生艇**——與其讓所有人都上船、然後船沉、大家一起淹死，不如控制人數，保住船上的人能活。殘酷但理性——**部分獲救，遠勝全部沉沒**。

進階做法會**依優先級卸除**：先丟棄低優先的請求（如背景任務、非付費用戶），保住高優先的（如結帳、付費用戶）。

---

### 這些機制怎麼配合 8-1

Part 8-1（重試、逾時、斷路器）保護你「**呼叫別人**」時不被拖垮；這一章的機制保護你「**被別人呼叫**」時不被淹沒。一個對外、一個對內，合起來讓系統在各種壓力下都能站穩：

```
別人呼叫你 → 限流（擋住異常來源）+ 負載卸除（整體過載時保命）
你呼叫別人 → 逾時 + 重試 + 斷路器（8-1，別被拖垮）
壓力過大時 → 優雅降級（關次要功能，保核心）
```

## 範例：大促時的層層保護

```
情境：電商雙 11，流量是平日的 10 倍，超過系統極限

系統的層層保命機制啟動：

① 限流：
   每個 IP 每秒最多 10 次請求 → 擋掉搶購機器人的瘋狂請求

② 優雅降級：
   偵測到高負載 → 自動關閉「個人化推薦」「商品評論」
   把資源全力留給「瀏覽 + 結帳」

③ 負載卸除：
   系統整體仍逼近極限 → 對「非結帳流程」的請求開始部分婉拒
   （顯示「人潮眾多，請稍候」），保住「正在結帳」的人能順利付款

結果：
  - 部分使用者體驗降級（看不到推薦、偶爾要重試）
  - 但「核心的買東西、結帳」對大多數人保持可用
  - 系統沒有崩潰 → 公司賺到了大促的錢
  
對比：如果沒有這些 → 系統被打爆 → 全站崩潰 → 誰都不能買 → 大促變大災難
```

## 小練習

### 練習 1：核心抉擇

用自己的話解釋：為什麼 SRE 說「服務 90% 的人，遠勝系統崩潰、0% 的人能用」？

<details>
<summary>參考解答</summary>

因為當流量超過系統極限時，只有兩種結局：**整個崩潰**或**優雅降級**。

- 若什麼都不做，系統被壓垮 → **所有人都不能用（0%）**，公司完全損失這段時間的服務與營收，這是最糟的結果。
- 若主動「犧牲一部分、保住大部分」——用限流、負載卸除、降級去婉拒或降級少數請求，就能讓**90% 的人正常使用**。

兩相比較，「90% 可用」在任何指標上都遠勝「0% 可用」：更多使用者被服務、更多營收被保住、系統沒有真的倒下（不需要痛苦地重啟恢復）。過載時的智慧不是「大家一起硬撐到一起死」，而是「**主動控制、保住多數**」。

用類比：這就像醫院急診爆滿時的**檢傷分類**——資源有限，先救命危的、輕症的等一下。硬要「一視同仁全部同時處理」的結果反而是誰都救不好。優雅降級就是系統版的檢傷分類：資源不夠時，優先保住最重要的核心功能與最多數的使用者。

</details>

### 練習 2：分清限流與負載卸除

回答：

1. 限流和負載卸除的差別是什麼？（提示：針對「單一來源」vs「系統整體」）
2. 各舉一個適合用它的情境。

<details>
<summary>參考解答</summary>

**1. 差別：**

- **限流（Rate Limiting）** 針對**單一來源**：限制「每個使用者/IP/來源在單位時間內能發多少請求」，超過就婉拒（回 429 Too Many Requests）。它是為了「公平」與防止單一來源吃掉所有資源，**不管系統整體現在忙不忙**都在把關。
- **負載卸除（Load Shedding）** 針對**系統整體**：當整體資源快撐不住時，主動丟棄一部分請求（常依優先級丟低優先的），保住剩下請求能被好好處理。它看的是「系統整體健康度」，是過載時的保命動作。

一句話：限流是「你這個來源發太多，擋你」；負載卸除是「整個系統快掛了，只好犧牲一部分請求救大局」。

**2. 情境：**

- **限流適合**：防惡意攻擊或失控的客戶端——例如某個搶購機器人（或有 bug 沒做退避的程式，呼應 8-1）瘋狂送請求，用「每 IP 每秒最多 N 次」把它擋在門外，保障其他正常使用者。
- **負載卸除適合**：突發爆量（如大促、熱門事件）讓系統整體逼近極限時——依優先級開始婉拒低優先請求（背景任務、非付費用戶、非結帳流程），顯示「人潮眾多，請稍候」，把運算力集中保住高優先的核心請求（如正在結帳的人）。

</details>

### 練習 3：設計降級策略

幫一個「線上影音平台」設計優雅降級策略：當系統過載時，哪些是「核心功能」要保住、哪些是「次要功能」可以先關？

> 提示：使用者最核心的需求是「能播放影片」，那哪些是可以犧牲的？

<details>
<summary>參考解答</summary>

先問一句話：使用者打開影音平台**最核心的需求**是什麼？是「**能順利播放影片**」。所有降級策略都圍繞著「保住播放」來設計。

**核心功能（過載時全力保住）：**

- **影片播放本身**：播放器啟動、影片串流（video streaming）正常送出——這是整個平台存在的理由，絕不能斷。
- **登入 / 驗證播放權限**（付費會員能不能看）——直接關係到能不能播與營收。
- **基本的影片搜尋 / 找到想看的片**——找不到片就無從播放。

**次要功能（過載時可先關閉或降簡化版）：**

- **個人化推薦 /「猜你喜歡」**：關掉改顯示「熱門影片」固定清單，或乾脆不顯示——使用者照樣能播他點進來的片。
- **留言 / 彈幕 / 評論區**：暫時關閉，最不影響核心播放體驗。
- **播放清單同步、觀看紀錄、按讚統計**：可先寫進佇列稍後補、或暫停即時更新。
- **高畫質選項**：過載時可暫時把預設畫質調降（例如強制 720p），用**降低品質換取更多人能穩定播放**——這本身也是一種優雅降級。
- **縮圖預覽 / 影片封面動態預覽**：載入這些很吃資源，過載時可退回靜態圖或省略。

**設計精神**：把資源集中在「串流出影片」這條命脈上，把「錦上添花」的功能（推薦、留言、動態縮圖、超高畫質）當作可調節的緩衝。使用者也許發現「推薦不見了、留言關了、畫質降了」，但他**還是能看片**——這遠勝「為了顯示推薦與 4K，結果整站過載、誰都播不了」。等流量退去再逐步恢復次要功能。

</details>
