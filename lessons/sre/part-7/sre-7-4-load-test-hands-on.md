# [sre-7-4] 🔧 動手做：對服務做負載測試，找出瓶頸

> **本章目標**：用負載測試工具實際對一個服務壓測，邊壓邊看監控，找出它的「天花板」與「瓶頸」，把 Part 7 的觀念變成實際操作。

## 你會學到

- 用 `k6` 寫並執行一次負載測試
- 設計「逐步加壓」的測試情境
- 一邊壓測一邊看 Part 3 的監控找瓶頸
- 從結果判斷天花板、瓶頸與下一步

## 概念說明

### 這一章在做什麼

Part 7-1 規劃了容量、7-2 講了負載測試的觀念、7-3 講了擴展。這一章你要**實際壓一次**——對一個服務逐步加壓，找出它撐到哪裡、卡在哪裡。

流程：

```mermaid
graph LR
    A["① 準備一個測試目標<br/>（你的服務）"]
    B["② 寫 k6 測試腳本<br/>逐步加壓"]
    C["③ 一邊壓一邊看監控<br/>（Part 3）"]
    D["④ 讀出天花板與瓶頸"]
    A --> B --> C --> D
```

> 在 WSL 或測試環境做，**別對正式環境壓測**（7-2 的警告）。用你 infra/SRE 前面部署的測試服務當靶子。

## 程式碼範例

### 第一步：安裝 k6

`k6` 是一個現代、好用的負載測試工具，用 JavaScript 寫測試腳本（你熟悉的語言）：

```bash
# Ubuntu / WSL
sudo apt update
sudo apt install k6 -y
# 或參考官方安裝方式
```

### 第二步：寫一個逐步加壓的測試腳本

建立 `loadtest.js`：

```javascript
import http from "k6/http";
import { check, sleep } from "k6";

// 測試設定：逐步加壓（7-2 的「逐步加壓」）
export const options = {
  stages: [
    { duration: "1m", target: 50 },   // 1 分鐘內，爬升到 50 個虛擬使用者
    { duration: "2m", target: 50 },   // 維持 50 個 2 分鐘
    { duration: "1m", target: 200 },  // 爬升到 200
    { duration: "2m", target: 200 },  // 維持 200
    { duration: "1m", target: 500 },  // 爬升到 500（加壓找極限）
    { duration: "2m", target: 500 },  // 維持 500
    { duration: "1m", target: 0 },    // 緩降結束
  ],
};

export default function () {
  // 模擬使用者請求（換成你的服務 URL）
  const res = http.get("http://localhost:3000/api/notes");

  // 檢查回應（這會被 k6 統計成成功率）
  check(res, {
    "狀態 200": (r) => r.status === 200,
    "延遲 < 300ms": (r) => r.timings.duration < 300,
  });

  sleep(1); // 模擬使用者操作間的停頓
}
```

幾個重點：

- `stages` 定義「逐步加壓」——從 50 → 200 → 500 個虛擬使用者，正是 7-2 的測試設計。
- `check()` 定義「什麼算成功」——對應你的 SLO（狀態 200、延遲 < 300ms）。
- 真實測試應模擬完整流程（登入→瀏覽→…），這裡簡化成單一請求示範。

### 第三步：執行並一邊看監控

跑測試：

```bash
k6 run loadtest.js
```

**關鍵：一邊跑，一邊開著 Part 3-6 建的 Grafana 儀表板看四個黃金訊號。** 你要同時觀察兩邊：

- **k6 的輸出**：每個階段的延遲（p95）、成功率、RPS。
- **你的監控儀表板**：延遲、錯誤率怎麼變？**哪個資源（CPU/記憶體/資料庫）先飆高、先飽和**？——這就是找瓶頸的關鍵。

### 第四步：讀懂 k6 的結果

測試結束，k6 會給一份摘要：

```
     http_req_duration..............: p(95)=850ms   ← 整體 p95 延遲
     http_req_failed................: 3.2%          ← 失敗率
     http_reqs......................: 45000  (約 250 RPS)
     ✓ 狀態 200 ... 96.8%
     ✗ 延遲 < 300ms ... 62%          ← 只有 62% 達到延遲目標！
```

對照各階段，你會看到類似 7-2 範例的結果——某個負載之後，延遲開始飆、失敗率上升。**那個轉折點就是你的天花板**。再對照當時監控上「哪個資源先飽和」，就是你的瓶頸。

---

### 第五步：產出結論

把發現寫成結論，這才是負載測試的價值：

```
負載測試結論：
- 天花板：約在 350 RPS（200 個虛擬使用者）後延遲開始劣化
- 瓶頸：資料庫 CPU 先到 95%（不是應用伺服器）
- 對照容量規劃：目前配置撐得住平日，但雙 11 預估會超過天花板
- 行動：
  1. 優化那個拖慢資料庫的查詢（或加讀取副本）
  2. 加上「優雅降級」保護（Part 8）防止超過天花板時雪崩
  3. 設定自動擴縮，並再壓測一次驗證（7-3）
```

## 小練習

### 練習 1：跑一次負載測試

對你 infra/SRE 前面部署的測試服務，用 k6 寫一個逐步加壓的測試並執行。觀察 k6 的輸出。

<details>
<summary>參考解答</summary>

這是動手題，重點是**真的跑一次**。以下是示範做法與該注意的地方：

**1. 準備 `loadtest.js`**（把 URL 換成你自己的測試服務）：

```javascript
import http from "k6/http";
import { check, sleep } from "k6";

export const options = {
  stages: [
    { duration: "1m", target: 50 },
    { duration: "2m", target: 50 },
    { duration: "1m", target: 200 },
    { duration: "2m", target: 200 },
    { duration: "1m", target: 500 },
    { duration: "2m", target: 500 },
    { duration: "1m", target: 0 },
  ],
};

export default function () {
  const res = http.get("http://localhost:3000/api/notes"); // ← 換成你的服務
  check(res, {
    "狀態 200": (r) => r.status === 200,
    "延遲 < 300ms": (r) => r.timings.duration < 300,
  });
  sleep(1);
}
```

**2. 執行**：`k6 run loadtest.js`

**3. 觀察 k6 輸出時要看的重點**：

- `http_req_duration` 的 `p(95)`：95% 的請求延遲。看它在哪個階段開始飆高。
- `http_req_failed`：失敗率。正常應接近 0%，飆起來代表系統開始撐不住。
- `http_reqs`：總請求數與換算出的 RPS。
- 你自己 `check` 的通過率（狀態 200、延遲 < 300ms）——對應你的 SLO。

**注意事項**：務必在 WSL 或測試環境對測試服務壓，**絕不要對正式環境壓測**（7-2 的警告）。第一次跑可以把 target 調小一點（例如 20/50/100）確認腳本能通，再逐步加大找極限。

（實際的數字會依你的服務與機器而不同，這題沒有「標準答案」——有成功跑出一份 k6 摘要、看得懂上面幾個指標，就達成目標了。）

</details>

### 練習 2：邊壓邊找瓶頸

壓測時，同時看你的 Grafana 監控（Part 3-6）。記錄：當延遲開始劣化時，是哪個資源（CPU/記憶體/資料庫/連線）先飽和？那就是你的瓶頸。

<details>
<summary>參考解答</summary>

這題的關鍵是**同時盯兩個畫面**：一邊是 k6 的即時輸出，一邊是 Part 3-6 建的 Grafana 儀表板（四個黃金訊號）。

**做法**：

1. 壓測前先把 Grafana 開好，看得到 CPU、記憶體、資料庫（連線數/CPU）、以及延遲與錯誤率這幾個面板。
2. 跑 `k6 run loadtest.js`，注意 k6 輸出中「延遲 p95 開始飆、失敗率上升」的那個時間點（對應某個階段的虛擬使用者數）。
3. 在**同一個時間點**回頭看 Grafana：哪個資源的曲線先衝到接近 100%（或先出現異常）？那個先飽和的資源就是**瓶頸**。

**示範記錄（你的結果會不同）**：

> 當虛擬使用者從 200 加到 500、延遲 p95 從 250ms 飆到 1,200ms 時，Grafana 顯示應用伺服器 CPU 只有 40%，但**資料庫 CPU 已經到 95%**、資料庫連線數也接近上限。→ 瓶頸是**資料庫**，不是應用層。

**要點**：延遲劣化只告訴你「撐不住了」，但**看監控才知道是哪裡撐不住**。最常見的瓶頸是資料庫（CPU 或連線數），但也可能是記憶體、磁碟 I/O 或連線池——以你實際看到「先飽和」的那個為準，不要用猜的。

</details>

### 練習 3：寫出結論

根據你的測試，寫出：

1. 這個服務的「天花板」大約在多少 RPS / 多少使用者？
2. 瓶頸是什麼資源？
3. 如果要提升容量，你會優先做什麼？（提示：針對瓶頸，不是盲目加機器）

<details>
<summary>參考解答</summary>

這題要你把前兩題的觀察整理成一份**負載測試結論**——這才是壓測真正的產出。示範（你的數字依實測而定）：

**1. 天花板大約在多少 RPS / 多少使用者？**

找 k6 輸出裡「延遲 p95 開始明顯飆高、失敗率開始上升」的那個轉折點，對應到當時的虛擬使用者數與 RPS。例如：

> 天花板約在 **350 RPS（200 個虛擬使用者）** 之後——超過這裡延遲從 250ms 飆到 1,200ms、失敗率開始上升。

**2. 瓶頸是什麼資源？**

對照練習 2 監控上「先飽和」的資源。例如：

> 瓶頸是**資料庫 CPU**（先到 95%），不是應用伺服器（CPU 才 40%）。

**3. 要提升容量，優先做什麼？**

**針對瓶頸下手，不是盲目加機器**。既然瓶頸在資料庫，加應用伺服器沒用（它們最後還是打同一個資料庫）。優先順序示範：

1. **優化那個拖慢資料庫的查詢**（加索引、改寫 SQL），或加**讀取副本**分攤讀取——最直接解掉瓶頸。
2. 加上**優雅降級**保護（Part 8），避免超過天花板時整個雪崩。
3. 設定**自動擴縮**（7-3），並**再壓測一次驗證**改善有效、且下游（資料庫）也撐得住。

核心觀念：先找到瓶頸、再對準瓶頸優化——「盲目加機器」常常花了錢卻沒解決問題，因為加錯了地方。

</details>
