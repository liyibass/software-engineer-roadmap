## 概念說明

### 你的 SRE 畢業專案

恭喜你走到 SRE 課的最後。回顧這趟旅程：你從「什麼叫可靠」開始，學會用數據定義它（Part 2）、觀測它（Part 3）、為它告警（Part 4）、處理事故（Part 5）、消除苦工（Part 6）、規劃容量（Part 7）、為失敗而設計（Part 8）、建立文化（Part 9）。

這一章，把所有東西**組裝成一個完整的「可靠性體系」**。目標是：拿一個服務，為它配齊一個專業 SRE 該建立的一切。


## 範例：完整的可靠性體系

針對一個服務（例如你的筆記 App API），逐項配齊。這就是一個專業 SRE 交付的「全套」：

### ① SLO 文件（Part 2）

```markdown
# 可靠性目標
- 可用率 SLO：99.9%（錯誤預算：每月約 43 分鐘 / 0.1% 請求）
- 延遲 SLO：p95 < 300ms
- Error Budget Policy：
  - 預算用 > 75% → 放慢上線、加強測試
  - 預算用光 → 凍結新功能，全員修穩定性
```

### ② 監控（Part 3）

```
依「四個黃金訊號」設計的 Grafana 儀表板：
- 延遲（p95，標出 300ms SLO 線）
- 流量（RPS）
- 錯誤率（標出 0.1% SLO 線）
- 飽和度（CPU / 記憶體 / 資料庫連線）
資料來源：Prometheus（應用輸出指標 + node_exporter）
```

### ③ 告警（Part 4）

```
基於 SLO、對症狀告警、分級：
- [page] 錯誤率 > 1% 持續 5 分鐘（叫醒人）
- [page] 延遲 p95 > 300ms 持續 5 分鐘
- [page] 錯誤預算快速燃燒（burn rate）
- [ticket] 磁碟預估 3 天內滿（工單，不叫人）
每條都附 runbook 連結。
```

### ④ Runbook + Postmortem 範本（Part 4、5）

```
- 每個 page 級告警，都有對應 runbook：
  「收到這個告警 → 怎麼判斷 → 怎麼止血 → 怎麼診斷 → 何時升級」
- 一份標準 postmortem 範本（摘要/影響/時間軸/根因/行動項目）
- on-call 制度：輪值表、升級路徑
```

### ⑤ 韌性設計（Part 8）

```
- 對外部呼叫：逾時 + 重試（指數退避）+ 斷路器
- 過載保護：限流 + 優雅降級（過載時關閉次要功能）
- 冗餘：Multi-AZ 部署 + 自動故障轉移
- 安全發布：金絲雀發布 + 快速回滾機制
```

### ⑥ 故障演練（Part 8）

```
定期的混沌實驗計畫：
- 砍掉一個實例 → 驗證負載平衡與自動重啟
- 模擬資料庫故障 → 驗證故障轉移與斷路器
- 每季演練一次，每次寫成記錄、找改善點
```

### 完整交付：一個 Git repo

把以上全部，整理成一個 repo（呼應 infra 課的「一切皆程式碼」）：

```
my-service-reliability/
├── slo.md                      ← SLO 與 error budget policy
├── monitoring/
│   ├── dashboards/             ← Grafana 儀表板定義
│   └── prometheus-rules.yml    ← 告警規則
├── runbooks/                   ← 各告警的處理手冊
│   └── high-error-rate.md
├── postmortem-template.md      ← 事後檢討範本
├── chaos/                      ← 混沌實驗腳本與記錄
└── README.md                   ← 整體說明
```

這個 repo 就是這個服務「可靠性的單一事實來源」——任何人接手，都能從這裡看懂「這個服務的可靠性是怎麼被經營的」。

## 小練習

### 練習 1：建立完整可靠性體系

為一個服務（你的專案或前面部署的測試服務），配齊本章的六項：SLO、監控、告警、runbook、韌性設計、故障演練。整理成一個 Git repo。

<details>
<summary>參考解答</summary>

這是畢業專案，成果因人而異，但這裡給你一份**解題大綱 + 檢查清單**，照著走就不會漏。目標是產出本章那個 `my-service-reliability/` repo 結構。

**動手步驟（建議順序）**：

1. **先挑一個服務當對象**：用你 infra/SRE 部署過的服務（例如筆記 App API）。範圍別貪大，一個服務配齊，勝過五個服務只做一半。
2. **① 寫 SLO 文件（`slo.md`）**：定可用率 SLO（如 99.9%）、延遲 SLO（如 p95 < 300ms）、把錯誤預算換算成具體數字（99.9% ≈ 每月 43 分鐘），並寫下 Error Budget Policy（預算用 > 75% 放慢上線、用光凍結新功能）。
3. **② 架監控（`monitoring/`）**：依四個黃金訊號（延遲、流量、錯誤、飽和度）做 Grafana 儀表板，資料來源 Prometheus（應用指標 + node_exporter），並在圖上標出 SLO 線。
4. **③ 設告警（`prometheus-rules.yml`）**：基於 SLO、對症狀告警、分級（page vs ticket），每條附 runbook 連結。
5. **④ 寫 runbook + postmortem 範本**：每個 page 級告警都有一份「怎麼判斷 → 怎麼止血 → 怎麼診斷 → 何時升級」的手冊；一份標準 postmortem 範本。
6. **⑤ 加韌性設計**：對外部呼叫加逾時 + 重試（指數退避）+ 斷路器；過載保護（限流 + 優雅降級）；冗餘（Multi-AZ + 故障轉移）；安全發布（金絲雀 + 回滾）。
7. **⑥ 排故障演練（`chaos/`）**：寫下混沌實驗計畫（砍實例、模擬 DB 故障），每次演練留記錄。
8. **寫 `README.md`**：串起全部，讓任何人接手都看得懂「這個服務的可靠性是怎麼被經營的」。

**自我檢查清單**：

- [ ] 六項（SLO / 監控 / 告警 / runbook + postmortem / 韌性 / 演練）都有實際產出，不是只寫「待辦」。
- [ ] SLO 有換算成具體錯誤預算數字，且有 Error Budget Policy。
- [ ] 監控是「黃金訊號」而非塞一堆虛榮指標（避開 9-2 反模式）。
- [ ] 告警是「症狀型、基於 SLO、分級」，不是上百條擾民告警。
- [ ] 每個 page 告警都連到一份 runbook。
- [ ] 韌性設計四類（逾時重試斷路器 / 過載保護 / 冗餘 / 安全發布）都有涵蓋。
- [ ] 全部收進一個 Git repo，README 能讓外人看懂——這就是「可靠性的單一事實來源」。

</details>

### 練習 3：（終極挑戰）跑一次完整演練

對你建立的服務，做一次完整的「可靠性演練」：

1. 用負載測試找出它的天花板（Part 7）
2. 做一次混沌實驗，驗證韌性（Part 8）
3. 針對演練中發現的問題，寫一份 postmortem 風格的改善計畫（Part 5）

能順利做到這些，你就通過了專業 SRE 的畢業考。🎓

<details>
<summary>參考解答</summary>

這是終極實作題，這裡給你一份**演練大綱 + 檢查清單**，把三步串成一個完整的可靠性循環：「找極限 → 破壞驗證 → 檢討改善」。

**第 1 步：負載測試找天花板（Part 7）**
- 用負載測試工具（如 k6、Locust）逐步加壓，觀察黃金訊號在哪個 RPS 開始劣化（延遲飆高 / 錯誤率上升 / 飽和度爆表）。
- 產出：這個服務的「天花板」數字，以及先撐不住的瓶頸（CPU？DB 連線？記憶體？）。

**第 2 步：混沌實驗驗證韌性（Part 8）**
- 挑一個你設計過韌性的地方主動破壞它，例如：砍掉一個實例（驗證負載平衡 + 自動重啟）、模擬 DB 故障（驗證故障轉移 + 斷路器）。
- 產出：韌性機制「有沒有如預期生效」的觀察結果——重點是**驗證假設**，發現「以為會自動轉移、其實沒有」正是演練的價值。

**第 3 步：寫 postmortem 風格的改善計畫（Part 5）**
- 把前兩步發現的問題，用 postmortem 格式寫下來：摘要 / 影響 / 時間軸 / 根因 / 行動項目。
- 重點是**無咎**（對事不對人）且**行動項目要能落地**（具體、有負責人、可追蹤）。

**檢查清單**：

- [ ] 負載測試有跑出具體的天花板數字與瓶頸，不是憑感覺。
- [ ] 混沌實驗是「先講好預期、再破壞、再對照結果」，而不是亂砍一通。
- [ ] 演練中若發現韌性沒如預期生效，有誠實記下來（這才是重點）。
- [ ] 改善計畫用 postmortem 格式，無咎、行動項目可落地。
- [ ] 整個循環（找極限 → 破壞 → 檢討）都留下記錄，收進你的 repo。

做到這裡，你就完整跑了一遍真實 SRE 的核心工作流——恭喜，畢業考通過！🎓

</details>

> 恭喜你完成整門 SRE 課程！你從「什麼叫可靠」開始，到能為一個服務建立完整的可靠性體系。你現在不只會讓系統「跑起來」（infra），更會讓它「跑得可靠」（SRE）。這是非常珍貴的能力——去把它用在你的系統、你的職涯上吧。
